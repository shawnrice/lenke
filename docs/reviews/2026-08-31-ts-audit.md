## 1. Systemic: prototype-chain lookups (`key in obj`, `obj[userKey]`) — THE headline

> **WON'T FIX — settled (user, re-confirmed 2026-09-16).** This whole class is closed:
> a property, GQL function or algorithm name that collides with an `Object.prototype`
> member (`toString`, `constructor`, `valueOf`, `hasOwnProperty`, `__proto__`) is not
> real-world input for this engine, and the cost of auditing every lookup — plus
> teaching the fuzzers to generate such keys, which would then report failures nobody
> intends to fix — is not worth paying against input that does not occur. The items
> below are kept as a written record of WHERE the pattern lives, so a future reader can
> see the class was surveyed and decided rather than missed. **Do not re-raise them**,
> and do not tick them: `[ ]` here means "known and declined", not "todo". Revisit only
> if someone brings a real case of these keys arriving from real data.

A plain object (`{}`) inherits `toString`/`constructor`/`hasOwnProperty`/`valueOf`/…
from `Object.prototype`. `'toString' in {}` is `true` and `({})['toString']` is a
function — with **no** patching, triggered by ordinary user data (a property named
`toString`, a GQL fn `toString`, an MCP algo `constructor`). Two harms: (a) a
**byte-identity break** vs the HashMap-backed Rust engine (which has no inherited
keys); (b) wrong values / mis-dispatch / rollback corruption. Fuzzers miss it (they
never generate reserved-word keys). Fix pattern already exists in-repo
(`executor.ts:284` `propPresent`, `projection.ts:380` `selectStep`, `protocol.ts` `Map`,
`temporal.ts:673`).

## 9. Planner: the range index has no selectivity check (found 2026-09-17, by benchmark)

- [x] **[high]** engine `opt` — a vertex RANGE index is seeded whenever one exists on
      the key, with no check on how much it will actually filter. Measured on a 200k-row
      `Person` fixture (`simd_index_probe` E40): `WHERE age > 98` (1% pass) is **9.8x
      faster** with the index (303us -> 31us), but `WHERE age > 50` (49% pass) is **3.7x
      SLOWER** (321us -> 1184us) — seeking 98,000 rows through the index costs more than
      scanning 200,000. Same shape with a GROUP BY on top (377us -> 1138us).
      The engine behaviour predates this week, but `IndexKind: 'range'` only became
      expressible from TypeScript on 2026-09-14, so a user can now declare the index and
      make their broad queries four times slower with nothing to show why. `cost.rs`
      already estimates cardinality — the seek decision needs to consult it.

  FIXED 2026-09-23. The seeding rule now consults the measured crossover before
  emitting a `RangeSeek` (`seek_beats_scan`), reusing the `seed_fraction` /
  `range_count_capped` probe built for orientation — the two rules ask the same
  question, so the constant is now `SEEK_MAX_FRACTION` rather than an
  orientation-specific name. Re-measured on the same 200k shape (E74):

  ```text
  query                             no index     indexed    ratio
  age > 98  (1% pass, selective)       220.9us      37.3us   5.92x
  age > 50  (49% pass, broad)          812.9us     813.9us   1.00x
  age > 50, GROUP BY                   407.4us     413.2us   0.99x
  ```

  The win is kept and the loss is gone: declaring an index no longer costs a broad
  query anything. Below `SEEK_FLOOR_NODES` (4,096) the rule declines to decide and
  keeps the old behaviour — a full scan of 1,000 nodes is ~1.9us and the worst seek
  over them ~6us, so choosing differently would churn plans over a difference
  nobody can measure.

  Guarded by two unit tests rather than the fuzzer: both branches are
  answer-equivalent by construction (a `RangeSeek` IS `Scan`+`Filter`), so this is a
  cost decision and `rewrite_fuzz` — whose fixture is below the floor anyway — is
  the wrong instrument for it.

  THE RULE, MEASURED (E64/E65, 2026-09-17). Two flat constants decide it: a scan
  costs **1.88 ns per node scanned**, a seek **12.2 ns per row returned**, both
  independent of selectivity. So for a bare filter the crossover is
  `1.88 / 12.2 = 15.4%` — and the sweep confirms it, the index winning 1.6x at 10%
  and losing at 25% (0.6x). An earlier guess of "~2%" was far too conservative.

  With an EXPAND downstream the index wins at EVERY selectivity measured (3.1x at
  one hop, 15.5x at two). That does not follow from the constants — both plans do
  the same downstream work, which ought to cancel — and the reason is item 11
  below: expanding from a FILTERED frontier costs 4.55-15.65 ns/edge against a
  seek's clean id list. So the second clause compensates for an engine
  inefficiency, not a property of indexes; fix that and the 15% rule likely
  applies everywhere.

  What the planner needs today: seek when estimated selectivity is under ~15%, OR
  when an expand follows. Both clauses use cardinality `cost.rs` already estimates.
  Fix before further index work: it is a regression shape, not an enhancement, and
  it is reachable today.

## 11. Exec: expanding from a filtered frontier is 16x an expand from a seek (2026-09-17)

- [ ] **[med]** engine `exec` — the per-edge cost of an `Expand` depends on what fed it.
      Measured (`simd_index_probe` E48, 200k nodes x 8 edges): 0.28 ns/edge when the
      count shortcut applies, 4.55 ns/edge from a frontier filtered at 99% (i.e. the
      filter removed almost nothing), rising to 15.65 ns/edge at 1%. A `RangeSeek`
      feeding the same expand does not pay this. It is why item 9's second clause
      exists — the index looks unbeatable downstream of a filter partly because the
      filtered path is slow, not because the seek is fast. Worth isolating before the
      seek rule is tuned, or the rule will be fitted to an artefact.
      ISOLATED (2026-09-17, E68). The honest control is the same plan shape with and
      without the residual filter — same seek, same expand, same rows — because E48's
      reference was the count SHORTCUT, not an unfiltered expand. Split that way the
      16x is two costs with two different fixes:

  ```text
  count   NO filter (degree sum)      31.1us
  count   residual IsLabeled         475.5us   15.3x
  project NO filter                  320.7us
  project residual IsLabeled         625.6us    1.95x
  ```

  **~~[high] a defeated count shortcut~~ — WITHDRAWN 2026-09-17, see E71.**
  The 15.3x is NOT a penalty. `count(*)` over a bare `Expand` sums adjacency
  LENGTHS: it is O(sources) and never looks at an edge. Any predicate on the
  hop's endpoint must look at every edge to know which endpoints to test. They
  are different questions, and the "fast" one is the cheaper question. E71
  shows it directly — hold the sources fixed, scale the degree:

  ```text
  degree   edges walked   no filter   filtered   ns/edge
       2          4,072      32.9us    196.4us      40.2
       4          8,101      32.2us    267.8us      29.1
       8         16,065      34.3us    460.4us      26.5
      16         31,901      34.1us    712.0us      21.3
  ```

  The unfiltered count is FLAT while the edge count grows 8x; the filtered one
  tracks edges. Nothing is recoverable unless an endpoint predicate can be
  answered without visiting edges.

  Four attempts are recorded before that conclusion, so none gets re-derived:
  folding the predicate into the degree sum (**3.1x WORSE**; full note next to
  `try_fused_count` in fastpath.rs), a sparse binary-search membership path,
  three settings of the dense/sparse threshold (all under 20%), and blaming
  the fixture's degenerate all-nodes label (E70 — a 2000-node label costs
  331us against the 200k label's 488us, so the bucket is not it either).

  This also withdraws the claim that one fix closed three things: the 8.5x
  `spelling_probe` cliff and item 10's unlabelled-far-node decline share this
  cause, and it is the same non-penalty.

  **[med] The filter itself is 1.95x on a projection.** 305us over 16,065 rows
  is ~19ns/row, roughly a binary search into a 200k-id label bucket. Real,
  small, and the only part of this item still worth doing. E48's per-edge
  numbers (4.55-15.65 ns/edge) stand, and are the same family as E71's 21-40.

## 10. Planner: the native engine does not orient a fixed-length pattern (2026-09-17)

- [ ] **[high]** engine `opt` — a predicate on the FAR end of a fixed-length pattern
      never reaches an index, because the native optimizer does not score both ends and
      reverse. Measured (`simd_index_probe` E58/E59, 200k nodes x 8 edges, range index on
      `age`): `MATCH (a:Person)-[:KNOWS]->(b) WHERE b.age > 98` plans as
      `Filter <- Expand <- Scan` and takes 1349us; the SAME query written
      `MATCH (b:Person)<-[:KNOWS]-(a) WHERE b.age > 98` plans as `Expand <- RangeSeek`
      and takes 31us. **43x at 1% selectivity, 52.7x at 10%, 6.3x at 50%** — identical
      answers, differing by the written direction alone.
      The TS engine already does this (`orient`/`reversePath` in
      `packages/gql/src/executor/matching.ts`, which scores both ends and reverses when
      the far end is more selective), and `PropertyIndex.md` documents the behaviour
      without saying it is TS-only — so this is also a doc claim the native engine does
      not honour. `reversePath`'s own caveat is the guide for scope: a variable-length
      segment keeps its written orientation.
      ONE HOP DONE (2026-09-17). `opt.rs` reverses a one-hop pattern whose far-side
      predicate is seekable (`orient_eligible`/`orient_apply`/`reverse_one_hop`, plus the
      `swap_slots` remap the codebase had deferred at opt.rs:1344), and `lift_seed_label`
      hoists an `IsLabeled` conjunct out of the reversed predicate onto the seed `Scan`
      so the ordinary seeding rule can emit the `RangeSeek` (whose `label` is required).
      Measured on the far-side count (E66, 200k x 8, range index on `age`):

  ```text
  far node UNLABELLED (b)          677us   Filter <- Expand <- Filter <- Scan
  far node LABELLED (b:Person)     499us   Filter <- Expand <- RangeSeek
  hand-written backwards            32us   Expand <- RangeSeek
  ```

  1652us -> 499us, and the `spelling_probe` cliff 40x+ -> 4.4x. Three notes on the
  shape of what is left:

  THE ORDERING WAS THE WHOLE BUG. The pass sits BETWEEN two fixpoints, and both
  halves are load-bearing. `(a:L)-[:T]->(b:M)` arrives as two stacked `Filter`s, so
  running orientation first (as the initial version did) meant the LABELLED form —
  the only form that can produce a seek — never matched the rewrite at all, and
  measured 2.7x SLOWER than the unlabelled one. It needs the first fixpoint to merge
  the filters, and a second one afterwards to seed the reversed scan.

  THE REQUIRED LABEL IS NOW THE USER-FACING RULE, not a blocker: a far-side
  predicate reaches the index iff the far node is written with a label. Worth a doc
  line in `PropertyIndex.md` next to the TS `orient` claim.

  RESIDUAL 499us vs 32us IS NOT AN ORIENTATION GAP. Both plans seek and both expand;
  the difference is the `Filter` the oriented plan keeps above `Expand` to re-check
  the ORIGINAL seed's label on the far end. That is section 11 (filtered-frontier
  expand cost, 4.55-15.65 ns/edge), and 15x is squarely in its measured range.

  IT FIRES ONLY ON A PROVABLE WIN (2026-09-17). Reversing an UNLABELLED far node
  was a regression, and the spelling probe caught it once the fixture was given the
  index it had been missing all along. Without a label the reversed seed is
  `Filter <- Scan { None }`, which no rule can seek, so the reversal buys a
  pre-filter while PAYING a residual `IsLabeled` above the hop — and that residual
  defeats the count shortcut. Which way it trades is pure selectivity, which the
  optimizer does not know here: `b.age > 98` (1% pass) went 1652us -> 669us, but
  `b.age > -1` (100% pass) went 788us -> **3805us, a 4.8x regression**. So
  `reverse_one_hop` now declines unless a label lifts onto the seed. Gating the
  speculative case properly needs a cardinality estimate, and cost.rs has one.

  TWO HOPS DONE (2026-09-17, E72) — and this was the big one.
  `reverse_one_hop` required an `Expand` directly over a `Scan`, so every
  longer pattern kept its written direction. Re-measured after the pushdown
  split, the gap was exactly the 83x that had been filed:

  ```text
  2 hops forwards    178357us  Filter <- Expand <- Expand <- Scan
  2 hops backwards     2155us  Filter <- Expand <- Filter <- Expand <- RangeSeek
  ```

  `reverse_one_hop` is now `reverse_chain`, built on the observation that
  makes the generalization safe: reversing an n-hop chain maps slot `i` to
  `n - i`, and for n <= 2 that is exactly ONE `swap_slots(_, 0, n)` — the
  ends trade places, the middle stays put. At n = 3 it becomes two
  independent swaps, which `swap_slots` cannot express, so three hops
  decline (with a test).

  **178357us -> 2148us, 83x**, and the forwards spelling now produces the
  SAME PLAN as the hand-written backwards one — so `spelling_probe` reports
  "identical optimized plan" rather than two times that happen to agree.

  Two things the work turned up, both worth keeping:

  **The decision is now a TRIAL REWRITE, not a re-derivation.**
  `orient_scan` used to restate `reverse_one_hop`'s conditions, and they
  drifted apart once: the decision said yes, the rewrite declined, and
  consumers were renamed around a pattern that never reversed. It now calls
  `reverse_chain` on a clone and believes the answer, which cannot drift,
  for one clone per candidate at plan time.

  **The integration probe was structurally blind to the bug that mattered.**
  The first two-hop version put the MIDDLE node's label on the far end,
  dropping rows. Every E72 assertion passed anyway, because `social_store`
  labels every node `Person` — so a dropped `(b:Person)` check changes no
  answer there. A four-node unit fixture with a selective middle label
  caught it immediately. Second time on this branch that a probe agreed and
  a unit test disagreed.

  THREE+ HOPS DONE TOO (2026-09-17), and three hops turned out to hold the
  largest gap in the repo: **263502us written forwards against 37us written
  backwards** at 50k nodes (the forwards form does not finish at 200k). Now
  59.5us, **4429x**, and plan-identical to the hand-written form.

  What was capping it was the RENAME, not the peeling. Reversing an n-hop
  chain maps slot `i` to `n - i`; a single `swap_slots(_, 0, n)` is that
  permutation only while n <= 2, and at n = 3 it is the WRONG one — it
  leaves slots 1 and 2 crossed. `swap_slots` is now a thin wrapper over a
  general `map_slots`, and orientation renames through `reverse_slots`,
  which expresses the whole permutation. No hop limit remains.

  A crossed middle returns wrong rows only when the middle nodes are
  DISTINGUISHABLE, so `spelling_probe`'s uniform fixture cannot show it;
  `orient_three_hops_does_not_cross_the_middle_slots` builds a graph with a
  decoy route carrying the same labels in the opposite order.

  THE REQUIRED LABEL IS GONE (2026-09-17, E73), and with it the last
  orientation gate. `RangeSeek`/`IndexSeek` carried `label: String`, which
  quietly meant an unlabelled pattern could never use an index:

  ```text
  MATCH (n:Person) WHERE n.age > 98      30.6us   RangeSeek
  MATCH (n)        WHERE n.age > 98     303.1us   Filter <- Scan
  ```

  Nothing about the index needed it. BOTH property indexes are keyed by
  PROPERTY, not by label, and `range_seek_ids`/`index_seek_ids` applied the
  label afterwards as a post-filter over the candidates — with an explicit
  shortcut for when the label covers every live node. The field is now
  `Option<String>`: **303us -> 26.3us (11.5x)** on a query shape as ordinary
  as `MATCH (n) WHERE n.age > 98`, and the unlabelled far-side hop
  **1710us -> 448us (3.8x)**.

  GATED ON MEASURED SELECTIVITY, NOT ON A PROXY. Removing the label
  requirement invalidated orientation's "no label, no reversal" rule, but
  dropping that outright regressed the unselective case 2.6x (`b.age > -1`,
  0.95ms -> 2.44ms) — reversing something that filters nothing still pays a
  residual check above the hop. The gate is now the thing the label was
  standing in for: the far predicate's actual share of the graph against
  E64/E65's 15.4% crossover (`ORIENT_MAX_FRACTION`), read through a new
  `Store::range_count_capped`, which ABORTS once the count passes the
  threshold — so an unselective predicate costs a bounded probe rather than
  a full index walk (the same early-abort trick `dict_encode` uses). When
  selectivity cannot be known — a parameterized bound — it falls back to the
  old label rule, so a parameterized query behaves exactly as before.

  The `spelling_probe` far-side cliff is 40x -> 9.2x across the three
  changes, and what remains is item 11's non-penalty, not a planning gap.

  A SHIPPED BUG IN THIS, found 2026-09-19 by the new optimizer fuzzer
  (`opt/rewrite_fuzz.rs`) and fixed: `peel_hops` and `shift_slot` both asked
  `max_slot(pred) == Some(endpoint)` where they meant "reads that slot and NO
  OTHER". A predicate over slots {1, 4} has a maximum of 4, so it was attributed
  to hop 4 and renamed as if slot 1 were not there — emerging as a read of slot 4
  at a point in the chain where only slots 0 and 1 exist, which panicked rather
  than answering wrongly, but only by luck. `reverse_chain` documents this exact
  trap for the FAR predicate, where a maximum of 0 is sufficient because 0 is also
  the minimum; a middle slot has no such luck. Now `reads_only_slot`.

  It is reachable only through a DISJUNCTION: a mixed `And` is taken apart by the
  per-conjunct pushdown split (item 12) before orientation sees it, so only a mixed
  `Or` arrives still reading both ends.

  MID-PATTERN SPLITTING DONE (2026-09-27) — see item 24.

## 65. An unknown edge type answered 0 where the pattern returns rows (2026-09-30)

The same class as item 64 with a different root cause, found by the 200,000-seed sweep once item
64's fix let a `min = 0` plan reach these fast paths: `optimizing_preserves_rows_across_shapes`,
seed 219640, 5 against 0.

`want_etypes` fails for an edge type the store has never seen, and three counting fast paths took
that as "no rows" and returned 0. It means "no edge is traversable", which is not the same thing: a
`{0,n}` quantifier also emits the ZERO-LENGTH path — the source itself, one row per source row,
needing no edge at all.

Measured on 4,000 vertices of degree 4, with `[:Nope]` naming no existing type:

| query                                      | count said |  rows |
| ------------------------------------------ | ---------: | ----: |
| `(x:N)-[:Nope]->{0,2}(y)`                  |      **0** | 4,000 |
| `count(DISTINCT y)` over the same          |      **0** | 4,000 |
| `((a)-[:Nope]->(b)){0,2} (t)`              |      **0** | 4,000 |
| `((a)-[:Nope]->(m)<-[:Nope]-(b)){0,2} (t)` |      4,000 | 4,000 |

Reachable with no endpoint filter and no big graph — the plainest possible query.

### The module already knew the answer

Four other sites in the same two files handle it the right way, with a sentinel: a want-set holding
one non-existent etype id (`u32::MAX`; etype ids are dense, so it is none of them) matches nothing,
so the walk traverses nothing and still emits whatever needs no edge. The aggregate twin's comment
even spells it out — "yielding the empty-aggregate value without a special-cased early return
here". `var_length`'s own comment says "lets the DFS traverse nothing yet still emit those".

So one question had two answers in one module, and the four sites that special-cased it were the
wrong ones. FIXED by adopting the sentinel at all of them, which removes the special case rather
than adding a second condition to it.

The nested group was already right, and that is what said the bug was in the shared want-set
handling rather than in the quantifier semantics: its walker emits at each outer-rep boundary, and
boundary zero is the source, with no want-set shortcut in the way. It is kept as a control test.

### Mutants

| site                                | mutant                      | caught by                                     |
| ----------------------------------- | --------------------------- | --------------------------------------------- |
| `try_varlen_count`                  | sentinel back to `return 0` | the row-agreement sweep + the absolute test   |
| `try_varlen_distinct_count`         | same                        | the row-agreement sweep                       |
| `var_length_count` (the group sink) | same                        | **nothing**, until a TWO-hop unit was added   |
| `try_varlen_distinctby_count`       | same                        | nothing — and `min == 0` is unreachable there |

The group-sink hole is worth the note: every group spelling in the first sweep is single-hop, and a
single-hop group FLATTENS onto a var-length hop, so it exercised `try_varlen_count` a second time
rather than the group's own sink. A `k = 2` unit cannot flatten, which is what reaches it.
`a_two_hop_group_count_agrees_with_its_rows_for_an_unknown_edge_type` uses a small fixture on
purpose — the two-hop row-returning form over a real edge type fans past the trail budget on the
4,000-vertex one, and that site has nothing to do with the algebraic branch a big graph is for.

`try_varlen_distinctby_count`'s mutant survives because `DistinctBy` is Gremlin's `dedup()`, and the
spellings that produce it give `min` of 1 (`emit()`) or `k` (`times(k)`) — checked, never 0. The
sentinel stays there anyway: it is correct either way, it makes the four sites say the same thing,
and it does not depend on that survey staying true.

### Separately: a divergence this run surfaced and did not cause

A random-seeded differential-fuzz run failed on

## 64. The algebraic var-length count omitted the zero-length path (2026-09-30)

Found while extending item 63's endpoint peel to `try_varlen_count`, and separated out because it is
a wrong answer that needs no perf work to reach.

`count(*)` over a var-length hop has an ALGEBRAIC path: for a bounded `OUT` walk or trail with
`max <= 2` the answer follows from out-degrees in O(V+E), with no path enumerated (it is why
`varlen count` is 587us rather than an enumeration). It counted only paths that TRAVERSE an edge. A
`{0,n}` quantifier also emits the zero-length path — the source itself as its own endpoint, one row
per source row — so the count was short by exactly the source count.

Measured on 4,000 vertices of degree 4, `MATCH (x)-[:R]->{0,2}(y) RETURN count(*)`:

|                         |      count |
| ----------------------- | ---------: |
| the algebraic fast path |     79,996 |
| the rows it is counting | **83,996** |

Exactly 4,000 short, the source count. Reachable today with no endpoint filter anywhere: the only
requirement is a graph big enough for `est_paths > 2 * (nodes + edges)` to choose the branch.

FIXED with the missing term, `if *min == 0 { total += src.len() as u64 }`. It is `src.len()`, the
SOURCE ROW count, not the node count: a repeated source row has its own zero-length path, which
`the_zero_length_term_counts_source_rows_not_nodes` pins with a `UNION ALL` of two scans.

### Why nothing had caught it

Three oracles cover this code and each misses it for its own reason, which is worth recording
because it is the same gap shape each time — a guard that cannot see the branch it is guarding.

- `rewrite_fuzz` compares raw against optimized over generated graphs, and those graphs are far too
  small for `est_paths > 2 * (nodes + edges)` to choose the algebraic branch. It never ran.
- The differential fuzzer's fixture is three vertices, for the same reason.
- The bench fixtures ARE big enough — and benches count rows and report times; they do not check
  answers. `varlen count` has been reporting a wrong number quickly for as long as it has existed,
  and a bench cannot tell.

It surfaced only because item 63's peel put a `min = 0` plan on this branch for the first time, and
then `rewrite_fuzz` did fail — on `optimizing_preserves_rows_*`, 102 against 42. So the fuzzer had
the teeth all along; what it lacked was a plan shape that reaches the branch, and a fast path
becoming reachable for one more shape is what supplied it.

The bench row added for it (`varlen count {0,2}`, 584us against the `{1,2}` row's 611us) is a cost
guard only. The answer guard is
`the_algebraic_count_includes_the_zero_length_path`, which sweeps `{0,2}`, `{1,2}`, `{0,1}`, `{1,1}`
and `{2,2}` and compares the fast path against the rows it claims to count — on a fixture large
enough to select the branch, which is the part the existing tests did not have.

| mutant                                              | caught by                                |
| --------------------------------------------------- | ---------------------------------------- |
| the zero-length term removed                        | the sweep + the source-row test          |
| `src.len()` replaced by the node count              | **only** the `UNION ALL` source-row test |
| the term gated on `min <= 1` rather than `min == 0` | the sweep                                |

`a_zero_only_quantifier_counts_exactly_the_sources` catches none of them, and says so in its own
comment: `{0,0}` has `max == 0`, which the algebraic gate excludes, so it exercises the enumeration.
It pins the semantic the algebra has to agree with rather than the algebra itself.

## 63. A counting sink that declined on an endpoint filter (2026-09-30)

Item 61's first open bullet, now closed for the group sinks. `try_group_count` matched an
`Aggregate` sitting DIRECTLY on a group, so any endpoint filter — `(t:Person)` and
`WHERE t.age < 10` both lower to a `Filter` above the group — made it decline and put the count
back on the materializing walk.

Sized first with a throwaway hack that peels the `Filter` and IGNORES its predicate — a wrong
answer, but the floor:

| row (50,000 vertices) |                 baseline | floor with the filter ignored |           |
| --------------------- | -----------------------: | ----------------------------: | --------: |
| `group count :label`  |                 14,444us |                         759us |       19x |
| `group count .prop`   |                 11,712us |                         764us |       15x |
| `nested count :label` |                911,360us |                     147,550us |      6.2x |
| `k2 count :label`     | **E_RESOURCE_EXHAUSTED** |                      51,341us | an answer |

FIXED for the two group sinks. `peel_endpoint_filter` lifts a `Filter` whose predicate reads ONLY
the group's `endpoint_slot` (via `opt::reads_only_slot`, now `pub(crate)` rather than a second
implementation), and `CountSink` applies it.

| row                            |              before |                                  after |
| ------------------------------ | ------------------: | -------------------------------------: |
| `nested count :label`          |           911,360us | **153,968us** (5.92x, floor 147,550us) |
| `k2 count :label`              |               ERROR |                           **60,904us** |
| `group count :label` / `.prop` | 12,029us / 11,073us |            unchanged — see open, below |

### Why per-endpoint rather than per-path

`CountSink::Hits` counts paths PER ENDPOINT NODE and evaluates the predicate once per DISTINCT
reached node at the end, in 4,096-node blocks, through `exec::filter_keep` — the Filter's own keep
computation, factored out so there is one answer to "which rows does this predicate keep" rather
than two. That bounds the evaluation by the node count instead of the path count (3,158,250
emitted paths over 50,000 vertices was the measured shape).

The tempting simplification is to precompute the predicate for EVERY node once. It is not
equivalent, and `an_endpoint_predicate_is_evaluated_only_for_reached_nodes` pins why: a predicate
can throw (`t.k + 1 <= 5` where `k` is a string is `arithmetic requires a number`), and evaluating
a node the walk never reaches would fail a query that answers today. That matters for the open lead
below, where precomputing over all nodes is exactly what the algebraic path would want.

### Nine mutants

| mutant                                              | caught by                                                                                                                                 |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| the peeled predicate is never applied               | 4 tests                                                                                                                                   |
| the peel ignores `reads_only_slot`                  | 2 tests + 8 `rewrite_fuzz` cases                                                                                                          |
| the nested sink tallies node 0 always               | 2 tests                                                                                                                                   |
| the per-endpoint multiplicity is lost               | 2 tests                                                                                                                                   |
| the endpoint is read from the START of the path     | **nothing**, until `skewed_label_store`                                                                                                   |
| the block loop stops after the first block          | **nothing**, until a >4,096-endpoint fixture                                                                                              |
| `BLOCK` shrunk from 4096 to 4                       | nothing — and correctly so: it is a tuning constant                                                                                       |
| an out-of-range endpoint clamped instead of dropped | nothing — unreachable; node ids are always below the node count, and the `u32::MAX` fallback is for an empty path stack that cannot occur |

Two of those were real holes and both came from the same source: a fixture regular enough to be
convenient is regular enough to hide which end of a path you read. `dense_store_mixed` alternates
labels by parity, and over it counting by the path's START and by its END give the SAME total by
symmetry. `skewed_label_store` breaks the symmetry deliberately — `0 -> 2`, `1 -> 2`, `2 -> 3` with
only vertex 3 carrying `M`, so the two paths both END at an `M` and both START at an `N`, and the
filtered counts are 2 and 0 depending on which end is read. Hand-derived, and the only test that
catches the mutant.

The block mutant is the mirror image: with `BLOCK = 4096` every fixture in the suite fits in ONE
block, so the multi-block path was never executed. Shrinking the constant to 4 leaving the suite
green did not show the constant is irrelevant — it showed the loop was uncovered.

### And the cross-engine oracle was passing for the wrong reason, again

The differential fuzzer's anchored arm generates `MATCH (a:T)((x)…){1,2}(b:T) RETURN count(*)`,
which after this change routes straight through the peel. Dropping the predicate entirely was
still GREEN over 20,000 queries.

Because every vertex in that fixture carries `T`. `(b:T)` is a filter that excludes nothing, so a
count with the predicate applied and a count with it dropped are the same number. Only vertex 3
carries `U`, so the arm now draws its endpoint from `['(b:T)', '(b:U)', '(b:U)', '(b)']`, with a
coverage pair (`peel=150-189 / 30-53` of 20,000, floors 75/15). With `(b:U)` in the draw the
dropped-predicate mutant diverges immediately: `ts: [{"x":1}]` against `native: [{"x":3}]`.

This is the same shape as item 61's finding at the same spot, and worth stating plainly because
the two are easy to confuse: item 61's problem was that the anchored spelling did not REACH the
sink, so a new spelling was added. This one is that the anchored spelling reaches it but over data
where the filter is vacuous. Reaching the code and exercising it are separate properties, and the
same generated query satisfied one and not the other at different times.

### Open, measured

`group count :label` and `group count .prop` did not move. A `{1,2}` single-direction unit flattens
to `VarLength`, whose count has an ALGEBRAIC degree-sum path (O(V+E) from out-degrees, which is why
`varlen count` is 587us rather than an enumeration), and that path has no way to take an endpoint
predicate — so the filter drops it to enumeration. The floor is 759us against 12,029us today,
about **16x**, and the shape is the most ordinary one a user writes.

The algebra extends: a filtered out-degree per node (`the count of a node's out-edges whose TARGET
satisfies the predicate`) replaces `outdeg[]`, and the 1-hop term counts only passing targets. That
needs the predicate evaluated for every node with an in-edge, not only for reached ones — which is
the equivalence the test above says does not hold in general. So it needs a fallback: attempt the
all-node evaluation, and on an error fall back to the enumerate-and-tally path, which evaluates
only what it reaches.

## 62. A label on a group's endpoint never reached the label fast path (2026-09-30)

Item 61's first open bullet was that an endpoint LABEL blocks the count shortcut, and measuring it
first found a different, larger bug underneath. On the 50,000-vertex degree-3 fixture:

| shape                                      | unanchored |        with `(t:Person)` |      |
| ------------------------------------------ | ---------: | -----------------------: | ---: |
| `((a)-[:KNOWS]->(b)){1,2} RETURN count(*)` |      601us |                 89,017us | 148x |
| `((x)-[:KNOWS]->(m)<-[:KNOWS]-(y)){1,2}`   |  147,930us |              1,341,788us | 9.1x |
| `((x)-[:KNOWS]->(m)-[:KNOWS]->(y)){1,2}`   |   55,360us | **E_RESOURCE_EXHAUSTED** |    — |

The fourth row is the one that named the bug: the SAME filter written as a property
(`(t) WHERE t.age < 10`) cost **11,421us** where the label cost 89,017us. Both lower to a `Filter`
above the group reading only the endpoint slot, so a 7.8x gap between them is not selectivity.

GQL emits `'Label' IN labels(slot)` for `(t:Label)`, and `normalize_pred` canonicalizes that to
`IsLabeled` — the same node Gremlin's `hasLabel` produces, and the form every fast path
recognizes. It is gated on `slot_is_node`, which is deliberately conservative: it returns true only
for shapes that PROVABLY bind a node, so an edge's label test is never turned into a node test. It
knew `Scan`, `Expand`, `VarLength` and `ShortestPath` — and nothing about a quantified group. So
the label test stayed boxed and the general evaluator built a label list per row.

This is the exact failure shape the repo guide names: the planner recognized one spelling of a
predicate and ran the general path for another that means the same thing, 100-300x, with the right
answer every time.

FIXED by teaching `slot_is_node` and `plan_out_width` about both group plans. A group carries its
`endpoint_slot` explicitly, so the node claim is exact — `slot == *endpoint_slot` — and the
trailing bind slots, which hold LISTS, fall through to the input, which does not claim a slot
beyond its own width.

| shape (50,000 vertices)           |      before |                 after |
| --------------------------------- | ----------: | --------------------: |
| `group count :label`              |    89,017us |   **14,444us** (6.2x) |
| `group count .prop` (the partner) |    11,421us |              11,712us |
| `nested count :label`             | 1,341,788us | **911,360us** (1.47x) |

The two spellings of an endpoint filter now cost the same, which is the point.

### Cross-engine, on one graph

The `k = 2` row is a parity gap, not only a slowdown. 12,000 vertices, degree 3,
`((x)-[:KNOWS]->(m)-[:KNOWS]->(y)){1,2} RETURN count(*)`, both engines over identical NDJSON:

|                                       |                  TS |                   native |
| ------------------------------------- | ------------------: | -----------------------: |
| no endpoint label                     | 1,609ms → 1,075,835 |     **13ms** → 1,075,835 |
| `(t:Person)` — which excludes NOTHING | 1,698ms → 1,075,835 | **E_RESOURCE_EXHAUSTED** |

A label that removes no rows turns a 13ms answer into a refusal, because the filter sits ABOVE the
group and `try_group_count` declines. That is item 61's lead, still open, and it is now a bench row
(`k2 count :label (open)`) that reports the error deliberately, the way `unbounded (guarded)` does.

### Six mutants, and the test each one needed

| mutant                                                         | caught by                                  |
| -------------------------------------------------------------- | ------------------------------------------ |
| the group endpoint is not claimed as a node (the original bug) | the two canonicalization tests             |
| EVERY appended slot claimed, not just the endpoint             | the bind-list test                         |
| only `RepeatGroup` learns, not `NestedGroup`                   | the nested canonicalization test           |
| `RepeatGroup` width forgets its bind columns                   | **nothing**, until the hop-above test      |
| `NestedGroup` width forgets its bind columns                   | **nothing**, until a second hop-above test |
| either width off by one in the other direction                 | both hop-above tests                       |

The two width mutants are why there are two tests asserting a SLOT NUMBER. `plan_out_width` is not
used by the group arm at all — it is used by a plan node ABOVE a group to find its own appended
endpoint — so a width wrong by the bind columns makes the hop above look at the wrong slot, and a
label test on the wrong column is a wrong answer rather than a slow one. Both tests also compare
the inline spelling's ROWS against the `IN labels()` spelling's, so a plausible-looking slot number
is not enough.

### What the spelling probe could not have found

`spelling_probe` gained the pair (`(t:Person)` against `WHERE 'Person' IN labels(t)`) because the
guide says a new predicate form belongs there. It is worth being exact that the probe could NOT
have found this bug: before the fix both spellings lowered to the same boxed form, so the probe
reported "identical optimized plan → identical exec" at 75ms exactly as it now does at 9.6ms.

A canonicalization that fails UNIFORMLY is invisible to an equivalence check. The guard for the
absolute cost has to be a pair of DIFFERENT predicates over one shape, where the gap between them
is the signal — which is what the `group count :label` / `group count .prop` bench pair is. The
probe's job here is the narrower invariant that the two label spellings never diverge from each
other.

That is the sixth distinct way in this run that something looked like coverage and was not, and the
first of its kind: not a shape never generated, nor a value that could not expose the bug, but an
oracle whose comparison is BLIND to the whole class by construction.

## 61. A nested group's count materialized every row too, and no oracle read the fix (2026-09-30)

The lead item 60 left measured next door: `k2-group count` at 52,977us sat beside `nested-group

The trail budget's own comment says it exists because a fan-out "materializes billions of rows and

enumeration terminates on its own.

The guard still applies where rows are genuinely materialized —

## 59. A named path read NULL above a join (2026-09-30)

Item 58 left `tracks_path` hardcoded false across a `Join` in `rewrite_fuzz`, with a comment
saying a join's lineage handling was "its own question". Asking it first, as the lead required,
found a wrong answer rather than a design choice.

`hash_join` built its output with `Batch::of`, which sets `lineage: None`. So EVERY path accessor
above a comma-pattern join read NULL — and a path read with no lineage is `Value::Null` per row
(exec/evaluator.rs), not an error, so the query parsed, ran, and returned a plausible-looking
column of nulls. Measured across engines on a three-vertex fixture:

| query                                    | TS                   | native (before) |
| ---------------------------------------- | -------------------- | --------------- |
| `size(nodes(p))` above a join            | `2` per row          | **`null`**      |
| `nodes(p)` above a join                  | the two element maps | **`null`**      |
| `path_length(p)` above a join            | `1` per row          | **`null`**      |
| `path_length(p)` over `->*` above a join | `1`/`0`/`1`          | **`null`**      |

TS is right: `p` is bound to one pattern, and joining on a shared variable has no business
destroying it.

FIXED: `hash_join` carries the lineage, gathered by `keep_l` / `keep_r` — the very row-index
vectors it already builds for the slot columns, so each output row keeps ITS OWN path. All four
shapes now agree across engines.

A `Batch` holds ONE lineage, so when both sides carry one only the LEFT survives. That is a
structural limit rather than a preference, and the left is the right choice because a named path
written before the comma lands there; two named paths across a join would need the sidecar keyed
by path variable, which is a larger change and is recorded rather than attempted.

With joins preserving lineage, `tracks_path` now propagates across one, so the oracle covers the
shape. Both mutations are caught:

| mutant                                                 | caught by                               |
| ------------------------------------------------------ | --------------------------------------- |
| drop the lineage again (the old `Batch::of` behaviour) | both named tests                        |
| gather the LEFT lineage by the RIGHT indices           | the element-content test + 4 fuzz tests |

The second is why one of the two tests asserts the path's FIRST element per row rather than only
its length: a lineage gathered with the wrong indices gives a plausible length and the wrong
nodes, and a length-only assertion would have passed.

### And two fuzzer arms that were comparing nothing

Checking the fix cross-engine turned up `relationships()` reported as an unknown FUNCTION by both
engines. The accessor is spelled **`edges`** in this dialect (`gql.rs` maps `"edges"` to
`PathPart::Relationships`); `relationships` is not a function name at all. So the pre-existing
`size(relationships(pp))` entry — and the `relationships(pp)` one added in item 58, mine — errored

Renamed to `edges(pp)` / `size(edges(pp))` and `elements(pp)` added. Measured after: **191-208
path-accessor queries generated per 20,000 and 191-208 of them returning ROWS, zero errors** — the
arm is now fully non-vacuous.

That is the fourth distinct way this run that something looked like coverage and was not: never
generated (item 51), generated over data that could not expose the bug (items 52, 56), the value

## 57. The remaining value-space gaps, and a float-to-text tie (2026-09-30)

Continuing the thread from items 51-56. Each remaining special value was added on its own and the
fuzzers run after each, so any failure could be attributed to one value.

### Settled cheaply, no change needed

- **Negative zero.** Reachable, but not the way the policy note implied: `SET n.k = -0.0`
  normalizes to `0`, while `SET n.k = 0.0 * -1.0` stores `Num(-0.0)` — a COMPUTED negative zero
  survives. It is invisible at the boundary though: both engines render it `0`, so there is
  nothing for a differential oracle to compare. Checked and dropped.
- **±Infinity.** Stores fine and compares correctly (`n.inf > 1e300` is true, `NOT` of it false),
  and both engines coerce it to `null` at egress. No divergence.
- **Empty, long, and surrogate-pair strings** added to `rewrite_fuzz`'s `tag` (which feeds
  equality seeks and dict encoding) and as stored `s` values on three new vertices in the
  differential fixture. All green. Worth noting `genString` already emitted a `'😀'` LITERAL, so
  the gap was narrower than it looked: surrogate pairs were covered on one side of a comparison
  and never on the other, because no stored value had one.
- **A map property with a missing key** was already covered — `genLeaf` generates `n.m.zz`.

### A stored NaN in the differential fixture, in two steps

NDJSON cannot express a NaN (ingest coerces it to null), so the only way in is to COMPUTE one:
the suite now runs `SET n.nan = sin(1e400)` on both engines after loading. Both store it and both
agree it `IS NOT NULL`, so the write side is symmetric.

Adding the value was not enough, and this is the iteration's lesson. With `n.nan` reachable only
through `genLeaf`, reverting item 55's fix left the suite GREEN — because the bug needs a bare
`NOT (<prop> <ordering op> <literal>)` as the filter predicate, which is the shape `genPred`'s
row-dependent arm builds and which `genExpr` almost never produces. **The value and the shape had
to meet.** With `n.nan` added to `genPred`'s comparison list as well, reverting the fix is caught
immediately:

```
MATCH (n:T) WHERE NOT (n.nan >= 3) RETURN n.n AS x ORDER BY x
    ts:     [{"x":3},{"x":7}]
    native: []
```

So the differential fuzzer now has teeth for the whole NaN-negation family, which it did not have
when item 55 was found (that one was caught by `rewrite_fuzz` only).

### The one real divergence found: a float-to-text tie

Raising the iteration count to 250,000 surfaced a byte-identity break, confirmed pre-existing by
reproducing it against the unmodified fixture:

```
FOR v IN CAST((9007199254740992 * 0.1) AS STRING) RETURN v AS x
    ts:     [{"x":"900719925474099.2"}]
    native: [{"x":"900719925474099.3"}]
```

The bits are IDENTICAL on both sides (`430999999999999a`); the exact value is …099.**25**, exactly
between two equally SHORT decimals, and both round-trip. ECMA-262 breaks that tie by choosing the
representation whose last digit is EVEN; Rust's `{:e}` rounds up. `CAST` already routes through
`json_fmt::js_number`, which places the decimal point exactly per the spec — it just inherits its
DIGITS from `{:e}`. Numeric egress agrees only because that path hands an f64 to the host and JS
formats it; only a value that becomes a string INSIDE the engine is affected.

ACCEPTED rather than fixed, and deliberately: telling a true tie from "very close to the midpoint"
needs exact decimal arithmetic over the f64's dyadic value, which f64 cannot do and which the
zero-dependency rule rules out importing. Guessing would change output that is currently correct.
The fuzzer's acceptance is narrow — a difference is excused only where every differing piece is a
numeric STRING and both spellings parse to the same f64, so a numeric string denoting a DIFFERENT
number is still reported. `float-text-tie.test.ts` pins the case, including that the numeric
projection does NOT differ, so a change in either engine's formatting fails a test rather than
being silently absorbed.

### Two build traps, both hit this round

Recorded because each cost a wrong conclusion:

- **`bun test <file>` does not rebuild anything.** Only `bun run fuzz` does. After reverting a fix
  to check teeth and then restoring it, a direct `bun test` ran against the `.so` built WITH the
  bug — which looked like a third, deeper bug in the FFI path and was not. The in-process Rust
  probe disagreed with it, and the probe was the freshly compiled one.
- **`cargo build --release` overwrites the FFI `.so` WITHOUT the `capi` feature**, silently
  removing the `lnk_*` exports, so every FFI test then fails with
  `Symbol "lnk_abi_version" not found`. The correct invocation is `bun run build:rust`
  (`--features capi`). `cargo test` never notices, because it links the lib rather than the
  cdylib.

## 55. The executor had its own copy of the NaN negation bug (2026-09-30)

Item 53 fixed `normalize_pred`, the PLANNER's `NOT (l <op> r)` → `l <negated op> r` rewrite. The
executor has a second one: `invert_pred` (exec.rs:4889), which does the same De Morgan +
operator flip to push a `NOT` into the typed filter fast path — its own comment says so
("`NOT p` pushes into the raw fast paths by inverting `p`").

Item 53's tests used `sin(1e400)`, a `Call`. `try_filter_keep` declines a `Call` argument, so
those tests never reached this path and the fix looked complete. With the NaN arriving from a
PROPERTY the fast path applies, inverts `<` into `>=`, and the row disappears:

```
MATCH (n:N) WHERE NOT (n.score < 3) RETURN n.name   ["hi"]          -- wrong
                                               want ["hi", "nan"]
```

FIXED the same way: `invert_pred` inverts only `=` and `<>`, which are genuine complements under
NaN. An ordering comparison returns `None`, so the caller evaluates the original `NOT` through
the general boxed path — which was always correct, and is why the raw plan (whose predicate was
an `And`, not a bare `Not`, and so fell through) got the right answer all along.

**Fixing the first copy hid the second.** That is the third time this run that one idea had two
implementations which had drifted apart — `rep_pred_ok` against `rep_ok` (item 51), the projected
`NOT` against the filtered `NOT` (item 53), and now the planner's negation against the
executor's. Worth a grep whenever a fix lands: is there another function that does this?

Test written before the fix and confirmed red: all four ordering operators, asserting both that
`NOT (NaN <op> k)` keeps the row AND that the positive complement does not — the two are not
complements, which is the entire point.

## 56. A NaN in a numeric column, and the estimate that counted it (2026-09-30)

Auditing the fixtures for value-space gaps, after three bugs in three items all came from a shape
being generated over data that could not expose it. `rewrite_fuzz`'s fixture holds `name` =
`n{i}`, `score` = `i % 7`, `tag` = `t{k}`, `age` = `i % 20` and sometimes absent. So: no NaN, no
±Infinity, no negative zero, no negative or fractional numbers, no empty or long or
surrogate-pair strings. For a fuzzer whose central invariant is seek-versus-scan agreement, range
predicates were only ever tested against small non-negative integers.

Adding NaN to `score` (every 11th node) failed FOUR tests immediately. A negative fraction alone
failed nothing, which isolated NaN as the cause.

Two distinct findings came out of it, and one candidate turned out to be fine:

- **The executor's `invert_pred`** — item 55, a wrong answer.
- **The estimate counted NaN as in range.** `range_count_capped` walks the range index, which is
  ordered by the TOTAL order where NaN sorts above every number, so an upward-unbounded bound
  (`> 5`) swept every NaN entry into the count. Measured: the true keep was **1051/8182 =
  12.9%**, under the 15.4% seek crossover, but the inflated count crossed the cap and the planner
  **declined a seek it should have taken**. A column containing any NaN therefore suppressed
  seeks on that key. Fixed by skipping NaN keys in the walk.
- **The range SEEK itself is correct** — verified, not assumed. It excludes NaN rows and agrees
  with the scan for all four ordering operators, so there was no wrong answer there.
  `a_range_seek_over_a_nan_column_agrees_with_the_scan` pins it.

### Stored NaN is reachable, which is what makes this worth fixing

The numeric model coerces NaN and ±Infinity to null on INGEST, so it was not obvious a stored
NaN could exist at all — and if it could not, the fixture would have been testing an impossible
state and the estimate "fix" would have been chasing a ghost. Checked rather than assumed:
`SET n.k = sin(1e400)` stores `Num(NaN)`. The coercion applies to host-supplied values, not to a
value computed by `SET`. So every finding above is reachable from ordinary GQL.

| mutant                                     | caught by                                                         |
| ------------------------------------------ | ----------------------------------------------------------------- |
| `invert_pred` inverts every operator again | its named test + 3 fuzz tests                                     |
| the range count includes NaN again         | `a_seek_is_chosen_exactly_when_the_predicate_is_selective`, alone |

The second is worth noting: the cost test caught a COST regression, which is exactly what it is
for, and no correctness test could have.

### Value-space gaps still open

Measured absent from both fixtures and not added here: ±Infinity, negative zero (the engine
normalizes it away by policy, so this one may be untestable by construction), an empty string, a
string long enough to exercise any length threshold, a surrogate-pair string (the one value class
where `utf16_len` differs from `len`), a list property containing null, and a map property with a

## 54. The predicate arms compared error codes, not data — 4-7% to 46-49% (2026-09-30)

Item 52's lesson applied to the rest of the differential fuzzer. Bucketing all 42 generator arms
by the selector value and splitting each arm's outcomes three ways — rows / empty / error —
found no arm that was fully vacuous, but three that were nearly so:

| arm                                    |     rows | empty |    error |
| -------------------------------------- | -------: | ----: | -------: |
| `MATCH (n:T) WHERE <expr>`             | **4-7%** |  ~18% | **~75%** |
| `MATCH (n:T) FILTER <expr>`            | **4-7%** |  ~18% | **~75%** |

context it usually produces something non-boolean and both engines reject it at parse (the static
boolean-context check). Those arms were comparing error parity far more than predicate
evaluation.

FIXED with `genPred`, a boolean-typed generator used in those three positions three times in
four — the remaining quarter stays on raw `genExpr` deliberately, so the boolean-context
rejection itself does not lose coverage. Its dominant arm is a ROW-DEPENDENT, TYPE-CONSISTENT
comparison (`n.n <op> 5`, `n.s <op> 'm'`, `n.n <op> n.x`, `n.m.k <op> 2`), and both halves of that
matter: a predicate over constants is all-or-nothing and says almost nothing about predicate
evaluation, and a cross-type comparison is a data exception by policy, which spends the sample on
the error path. The rest is `IS` tests, `NOT`, `AND`, `OR`.

| arm                  | rows before | rows after |
| -------------------- | ----------: | ---------: |
| `WHERE`              |         ~5% |    **46%** |
| `FILTER`             |         ~4% |    **49%** |
| inline `(n WHERE …)` |         ~7% |    **49%** |

Errors fell from ~75% to ~28%, so error parity stays well covered. Aggregate floors added
alongside item 52's: measured 3,891-4,045 predicate queries generated of 20,000 with 2,039-2,061
returning rows, floors at 2,000 and 1,000.

### It found a wrong answer immediately

The first run after `genPred` went in reported a divergence, and it was item 53's NaN bug:

```
MATCH (n:T) FILTER NOT (sin(1e400) >= 2) RETURN n.n AS x ORDER BY x
    ts:     [{"x":3},{"x":5},{"x":7}]
    native: []
```

The shape needed is `NOT` over an ordering comparison whose operand is NaN. At 4-7% rows the
combination was too rare to land; at 46-49% it arrived in the first 250,000 queries.

A process note, because it cost a detour: the first sighting was lost. The run was piped through
a `grep -E 'PRED|fail'` that discarded the divergence detail, and the next 39 runs (780,000
queries) did not reproduce it. Re-hunting with full output captured to files found it on the
second run of 250,000. **When chasing an intermittent failure, save the whole log.**

### Where this leaves the "generation is not coverage" thread

Three consecutive items were the same mistake wearing different clothes:

- item 51's bug needed a per-rep `WHERE`, which was never generated at all;
- item 52's reverse-hop unit WAS generated, and matched no rows because the fixture could not
  satisfy it;
- item 53's `NOT`-over-a-comparison WAS generated by `rewrite_fuzz`, over data (`score`) that is
  never NaN, so both spellings always agreed.

Reachable shape, unreachable bug, three times. The counters added in items 52 and 54 measure the
second thing rather than the first, which is the only version of the check that would have caught
any of them.

## 53. Negating an ordering comparison is wrong when an operand is NaN (2026-09-30)

`normalize_pred` rewrote `NOT (l <op> r)` to `l <negated op> r` for EVERY comparison operator.
Its comment enumerated the cases that had been checked — a NULL operand leaves both spellings
UNKNOWN, cross-type equality stays no-match, cross-type ordering throws either way — and **NaN
was not among them.**

Under IEEE unordered comparison, which is this engine's documented policy, a NaN operand makes
`<`, `<=`, `>` and `>=` ALL false. So `NOT (NaN >= 2)` is TRUE while `NaN < 2` is FALSE: the
rewrite turned a matching row into no rows.

The projected form was always right, which is what makes it sharp:

| query                          | result                                   |
| ------------------------------ | ---------------------------------------- |
| `RETURN (sin(1e400) >= 2)`     | `Bool(false)` — correct                  |
| `RETURN NOT (sin(1e400) >= 2)` | `Bool(true)` — correct                   |
| `WHERE NOT (sin(1e400) >= 2)`  | **`[]`** — wrong, the row should survive |

Only the FILTER went through `normalize_pred`, so evaluation and filtering disagreed on the same
expression.

FIXED by restricting the rewrite to `=` and `<>`, which ARE genuine complements under NaN
(`NaN = x` is false, `NaN <> x` is true). That keeps the case the rewrite exists for — the
comment's own example, `NOT d.name <> 'n929'` becoming the seekable `d.name = 'n929'`, so the two
spellings cost the same — and `equality_is_still_negated_into_the_comparison` pins it. The
ordering operators keep their `Not`, which is not seedable; that is a cost the correct answer
requires.

### Both fuzzers were blind, for different reasons

This is an optimizer rewrite changing the answer, which is precisely what `rewrite_fuzz` exists
to catch. It did not, **even at 200,000 seeds**. And its generator was already emitting the exact
shape: arm 7 of `gen_pred_kind` is `Not(Compare { Lt, Prop{score}, Lit })`. What it never
generated was a NaN VALUE — the fixture's `score` is always a well-behaved number, so the two
spellings agreed on every row and the fuzzer stayed green for the whole life of the bug.

That is the third time in three items that a generator produced the right SHAPE over data that
could not expose the defect (item 52's reverse-hop unit matched no rows; item 51's bug needed a
per-rep filter that was never generated). **The shape being reachable is not the same as the bug
being reachable.**

Closed on both sides:

- `rewrite_fuzz`: arm 7 now varies the operator across all six and, one time in three, uses
  `ln(-1)` — a NaN — as the left operand. With the fix reverted it fails at **seed 51**,
  immediately, on `optimizing_preserves_rows_{with,without}_indexes`, `_across_shapes` and
  `_across_sizes`. Green with the fix, including a 200,000-seed sweep.
- The TS-vs-native differential fuzzer found the bug in the first place, once its predicate arms
  started generating `NOT` over a comparison at a realistic rate — see item 54.

### Tests

Three in `exec/tests.rs`, written before the fix and confirmed red against it:

- `not_over_an_ordering_comparison_is_true_when_an_operand_is_nan` — all four ordering operators,
  with the NaN arriving both from a literal (`sin(1e400)`) and through a property (`ln(n.neg)`).
- `a_projected_not_and_a_filtered_not_agree_on_nan` — pins the projection and the filter together,
  which is where the divergence was visible.
- `equality_is_still_negated_into_the_comparison` — `=` / `<>` must STILL canonicalize, or the
  fix would have cost the seeding win. Worth noting the first version of this test asserted the
  plan still contained a `Compare`; it does not, because `NOT (k <> lit)` collapses all the way
  to an `IndexSeek`. That collapse is the point of the rewrite, so the assertion is that no `Not`
  survives and a seek is reached.

## 52. The differential fuzzer generated the broken shape and matched nothing with it (2026-09-30)

Item 51's bug was a native-vs-TS divergence that the differential fuzzer did not catch. The
obvious reading was that it never generated the shape. That was wrong, and the real answer is
worse: **it generated the shape and the shape matched no rows.**

The mixed-direction group generator has been emitting `(a:T)((x)<h1>(m)<h2>(y)){n,m}(b:T)` over
all sixteen direction/type pairs for some time. Two things made that coverage empty where it
mattered:

- **No per-repetition `WHERE` was ever attached**, which is the construct that broke.
- **The fixture could not satisfy a reversed second hop.** With three nodes and two edges no
  vertex had two distinct in-edges, and in Trail mode `(x)-[:E]->(m)<-[:E]-(y)` then has nowhere
  to go. Measured over all sixteen pairs: **4 of 16 matched anything, and the
  forward-then-reverse pair specifically matched 0 rows.**

So even with a per-rep filter added, the comparison would have been a wrong answer agreeing with
a wrong answer on an empty result.

FIXED, both halves:

- One edge added to the fixture — a SECOND in-edge into vertex 3 (`1 -> 3`, `E`, `w: 9`). Non-empty
  pairs went **4/16 to 8/16**, and the forward-then-reverse pair from **0 rows to 2**.
- The generator now attaches a per-rep `WHERE` two times in eight, over a NODE property, an EDGE
  property (the first hop's edge is named `e1` for this), and a mix — because node and edge
  bindings land in different columns of the per-rep mini-batch and that distinction is exactly
  what item 51 got wrong.

### Coverage floors, and why there are TWO

| counter                                 | measured over 3 runs of 20,000 | floor |
| --------------------------------------- | -----------------------------: | ----: |
| per-rep group queries GENERATED         |                  725, 769, 759 | > 350 |
| ...of which returned a NON-EMPTY result |                  365, 358, 368 | > 175 |

The second floor is the point of this item. Generation alone is not coverage — this fuzzer
generated the shape for a long time and compared nothing, because the shape matched nothing.
A density floor that counted only generation would have read as healthy throughout.

The first counter was also initially measured WRONG: a `/\)\s+WHERE\s/` regex over-counts by
about four times, since an ordinary `MATCH (n:T) WHERE …` looks identical. Detecting `((x)` plus

### Teeth, demonstrated directly

Reverting item 51's fix and re-running:

### A sibling-bug check that came up empty

Item 51's cause was two implementations of one idea diverging: `rep_pred_ok` (typed columns) and
`rep_ok` (boxed). Every other `Batch::of` mini-batch construction in `exec/` was checked for the

per-rep LISTS, which genuinely belong boxed. The class was isolated to `rep_ok`. Recorded so the
next person does not re-derive it.

## 51. FIXED: a per-rep WHERE over a reversed hop pruned every repetition (2026-09-30)

Item 50's bug. A per-repetition `WHERE` on a quantified subpath unit containing a REVERSED hop
returned zero rows for ANY predicate, including trivially true ones. The shape parsed, ran, and
returned a plausible number — nothing covered it.

### Cause, confirmed rather than guessed

Item 50 guessed the mini-scope slot mapping (node at `2p`, edge at `2p+1`). That guess was
WRONG twice over:

- That mapping belongs to `parse_subpath_group`, which **rejects mixed hop directions** outright
  ("a subpath group with mixed hop directions is not supported"). A reverse-hop unit never
  reaches it — it lowers through a second, more general path to `Plan::NestedGroup`, whose
  per-rep predicate is parsed against the OUTER scope with group depths decremented, and so
  references the outer `bind_slots`, not a mini-scope.
- The slots were bound correctly. Instrumenting `rep_ok` showed
  `pairs: [Null, Null, Num(0.0), Num(1.0), Num(2.0), Num(1.0)]` against a predicate reading
  slot 2 — the right node id, in the right slot — and `eval = Ok(Null)`, not an error.

The actual cause is the COLUMN TYPE. `rep_ok` built its per-rep mini-batch as
`cols[s] = Col::Gen(vec![v])`, so a node id arrived as a bare `Value::Num` in a boxed column.
`Prop` does not read that as an element, so `x.name` was NULL, NULL is not true, and every
repetition was pruned. The single-direction path never had the bug because `rep_pred_ok`
(exec/varlen.rs) builds `Col::Nodes` / `Col::Edges` — typed columns. The two implementations of
the same idea had silently diverged.

FIXED: `unit_slot_kinds` walks a `GUnit` (recursively through nested `Sub`s) for which slots hold
nodes and which hold edges, and `rep_ok` puts a SCALAR binding in the matching typed column. A
binding one nesting level deeper is genuinely a list in the per-rep view and stays boxed.

### It was a native-only divergence from the TS engine

On the hand-computed 4-node fixture, `count(*)` over `((x)-[e:R]->(m)<-[:R]-(y)){1,1}` with no
filter / `WHERE e.w > 5` / `WHERE e.w > 50`:

| engine         | unfiltered | `w > 5` | `w > 50` |
| -------------- | ---------: | ------: | -------: |
| pure-TS        |          2 |   **1** |        0 |
| native, before |          2 |   **0** |        0 |
| native, after  |          2 |   **1** |        0 |

So the TS engine had it right all along and this was a byte-identity divergence — **which no
fuzzer caught**, because none generates a per-rep `WHERE` over a reverse-hop unit.

> **CLOSED — item 52 (2026-09-30), and the reason was worse than "not generated".** The
> differential fuzzer HAD been generating reverse-hop units; its fixture just could not satisfy
> one, so the shape matched 0 rows and compared nothing. Worth noting
> alongside the other oracle-reach findings in items 38, 39 and 42: the differential fuzzers cover
> the surface they generate, and this corner was not on it.

### Tests

Written BEFORE the fix and confirmed red against it (0 vs 26, and 0 vs 1):

- `a_trivially_true_per_rep_filter_over_a_reversed_unit_keeps_every_rep` — both a NODE property
  and an EDGE property, since the two land in different typed columns.
- `a_selective_per_rep_filter_over_a_reversed_unit_prunes_exactly_those_reps` — hand-computed on
  a 4-node fixture: only `v2` has two distinct in-edges, so the reps are (v0, w=10, v2, v1) and
  (v1, w=1, v2, v0); `e.w > 5` keeps exactly the first.
- `per_rep_filters_on_forward_and_single_hop_units_are_unchanged` — the shapes that already
  worked, as the control.

| mutant                                        | caught by               |
| --------------------------------------------- | ----------------------- |
| revert to `Col::Gen` for every binding        | both new tests          |
| swap the node and edge kinds                  | both new tests          |
| omit the unit's start slot from the node list | the trivially-true test |

Fixture notes that cost three attempts in item 50: the per-rep `WHERE` goes after the unit
INSIDE the parens (inside the edge brackets is a per-HOP predicate and does not parse there); a
plain chain cannot satisfy a reverse-hop unit at all in Trail mode, since the reverse hop has no
second in-edge to take, so the fixture needs two in-edges per node; and `store::Builder` cannot
attach edge properties, so it has to be NDJSON.

### Item 50's guard is lifted

The `per_rep_pred.is_none()` condition on the NestedGroup unread-bindings rewrite existed only
because this bug made its safety untestable — the code comment said so. With the bug fixed,
`a_per_rep_filtered_nested_group_still_drops_unread_lists` shows the lists still drop under a
per-rep filter and the count is unchanged (the grouped form, which reads a list and so keeps
them, agrees), so the guard is removed and the rewrite now fires on those queries too.

## 50. A nested group built its lists unread too, and a per-rep WHERE over a reversed hop returns nothing (2026-09-30)

### The optimization: 1.83x

| query                                                                 |           count |

## 49. Evaluating a slot argument cloned the whole column — 1.26-1.45x (2026-09-30)

Item 48's open lead, generalized. `Expr::Slot(n) => batch.slot(*n).clone()` copies the entire
column every time a slot is evaluated; for a `Col::Gen` of `Value::List` that is one `Vec`
allocation PER ROW, paid before the function does anything. Item 48 dodged it for
`size`/`cardinality` with a special case; every other function over a boxed column still paid.

Measured first, in an isolated probe over a group-bound list column (599,998 rows, min-of-3 per
side, same binary and fixture). The floor for these is ~83.8ms, not the 15.1ms a literal
projection costs, because reading the list also forces the group to BUILD it (item 47):

| function                              | baseline | over the floor | with the borrow |   speedup |
| ------------------------------------- | -------: | -------------: | --------------: | --------: |
| `head(b)`                             |    142.1 |             56 |        **97.9** | **1.45x** |
| `reverse(b)`                          |    141.1 |             57 |       **104.4** | **1.35x** |
| `last(b)`                             |    136.9 |             53 |       **104.1** | **1.32x** |
| `tail(b)`                             |    120.3 |             36 |        **95.6** | **1.26x** |
| `size(b)` (already borrowed, item 48) |     85.7 |             ~2 |            84.7 |         — |

`head` and `last` return ONE element and should cost what `size` costs; that they sat 53-56ms
above the floor was almost entirely the clone. `tail` and `reverse` genuinely build a new list
per row, so part of their remaining gap is real work.

FIXED with a `Cow<Col>` argument path in the generic scalar-call loop: a bare-slot argument is
BORROWED, anything else is evaluated as before. `Cow` rather than an all-arguments-are-slots
check so a MIXED list still borrows the slots in it — the per-argument decision costs nothing,
and the all-or-nothing form would have skipped every call with a literal in it.

Observationally identical by construction: the `Slot` arm of `eval` does nothing but clone that
column, and `batch.slot` is the same accessor either way, so a missing slot still panics in the
same place.

### The bench row is a tripwire, not the measurement

A pure performance change has no correctness test that fails when it stops firing, so
`repeat-group head(b)` was added to `query/shortest`. But its numbers are NOT the measurement
here: across three baseline runs that row ranged 107,761-140,606us, a **30% spread**, because
the bench group runs many cases in one process and the allocator state varies. The isolated
probe above ranged under 3%. Per the noise-floor rule, the bench row is the regression
tripwire — a return to ~142,000us means the borrow stopped happening — and the probe is the
number.

### Two mutants, and the second needed a new assertion

| mutant                                   | caught by              |
| ---------------------------------------- | ---------------------- |
| borrow slot 0 instead of slot `k`        | both named tests       |
| borrow the LAST slot instead of slot `k` | **initially survived** |

The second survived because every query in the new tests referenced `b`, which IS the last
slot — so "the last column" and "slot `k`" were the same column and the mutation was invisible.
Fixed by also asserting `head(a)` differs from `head(b)`: `a` is bound at a LOWER slot and holds
the source nodes rather than the targets. With that assertion the mutant fails. Same shape as
item 48's surviving wrong-slot mutant, except there the wrong slot made the fast path DECLINE
(so the answer stayed right) and here it silently reads the wrong column — worth distinguishing.

Poisoning the borrow branch showed exactly two tests reach it: the two added here. Nothing else
in the suite calls a scalar function with a bare-slot argument, which is worth knowing — the
broad scalar-function tests pass either way and are not evidence for this path.

### Still open

`Value::List` remains `Vec<Value>`, so the PER-ROW value clone in
`buf.extend(cols.iter().map(|c| c.value_at(i)))` is untouched — that is the 14-18ms these
functions still sit above the floor. Removing it needs either `Arc<Vec<Value>>` for
`Value::List` (touching equality, ordering, rendering and TS/Rust byte-identity, so the full
fuzzer suite) or a by-reference `call_scalar` taking `&[&Value]`. Neither attempted; the table

## 48. Reading a list's length deep-copied the list — 1.44x (2026-09-30)

The other half of item 47's decomposition. `size()` cost ~73ns a call (44.1ms over 599,998
rows) where reading a `Vec` length should be nearer 1ns. Two causes, both in getting the
ARGUMENT rather than in the function:

- `Value::List` is `Vec<Value>`, not an `Arc`, and `Col::value_at` is
  `Col::Gen(v) => v[i].clone()`. So the generic per-row call loop DEEP-COPIED each list —
  allocate a fresh `Vec`, copy every element, read `len()`, drop it.
- `eval` on an `Expr::Slot` is `batch.slot(n).clone()`, which clones the whole COLUMN. For a
  boxed list column that is one `Vec` allocation and copy per row, paid before the function
  runs at all. **That clone is on the path of every function over a boxed column, not just
  this one** — see the open lead below.

FIXED with a by-reference arm for `size`/`cardinality` over a `Col::Gen`: borrow the column
when the argument is a bare slot, and map lists to their length without materializing a
`Value`. Isolated A/B, only the arm disabled, three runs each, min-of-3 (the baseline's own
spread was 9%, so this is the conservative reading):

| row                    | baseline | with the arm |   speedup |
| ---------------------- | -------: | -----------: | --------: |
| `repeat-group control` |   99,254 |   **68,826** | **1.44x** |
| `varlen control`       |   15,203 |       15,368 | unchanged |

Both halves of item 47's `((a)-[:R]->(b)){1,2} RETURN size(b)` row are now addressed: the list
BUILDING when unread (item 47, 4.46x) and the list-length READ here.

### Two dead arms, found by mutation and then deleted

The first version reproduced `call_scalar_checked`'s full semantics inline — a `Value::Str`
arm counting UTF-16 units, and a hard `E_INVALID_VALUE` for anything else, since `size()` of a
number is a data exception and NOT a null. Mutating both showed neither was reachable:

| mutant on the first version                    | result                       |
| ---------------------------------------------- | ---------------------------- |
| count a string's BYTES instead of UTF-16 units | **survived the whole suite** |
| turn the type error into a null                | **survived the whole suite** |

A string argument evaluates to `Col::Str`, not `Col::Gen`, so the fast path never sees one; and
no query shape puts a non-null non-string non-list into a `Col::Gen`. So both arms were dead
code duplicating semantics that already had one correct implementation.

Replaced by a pre-scan: take the arm only when every value is a list or null, and let anything
else fall through to the generic path. That deleted the duplication AND measured FASTER —
68,826us against 78,002us for the version with the extra arms, because the inner loop lost its
per-value error branch. The pre-scan itself is a discriminant check per row with no allocation,
against the ~51ns a row the clone was costing.

### The pre-scan guards a REACHABLE bug, and needed a test built for it

Dropping the pre-scan initially survived everything too, which would have made it look
defensive. It is not: a `CASE` yields `Col::Gen` of `Value::Str`, so without the pre-scan a
boxed string column maps every non-list to null and
`size(CASE WHEN … THEN 'ab' ELSE 'cde' END)` returns NULL instead of 2 and 3.

| mutant on the shipped version     | caught by                |
| --------------------------------- | ------------------------ |
| off-by-one on the list length     | 14 tests                 |

The last one deserves naming rather than a fix. Borrowing the wrong slot makes the arm DECLINE

### Open: `eval` on a Slot clones the whole column

> **FIXED — item 49 (2026-09-30), 1.26-1.45x across the list functions.** The per-ROW value
> clone below it remains.

`Expr::Slot(n) => batch.slot(*n).clone()` (exec/evaluator.rs) is the general form of the second
cause above. For typed columns that is a `Vec<u32>`/`Vec<f64>` memcpy; for `Col::Gen` of

above is the size of the prize for ONE function.

## 43. A size-only path read no longer builds the chain — 3.1x (2026-09-30)

The payoff item 41 measured and item 42 made safe to build. `path_length(p)` and
`cardinality(p)` need a number, and the BFS's `dist[&node]` already holds the hop count — yet
every emitted row walked back through the predecessor map to rebuild a chain that was then
reduced to its length.

`Plan::ShortestPath` gains `path_need: PathNeed`, set by `set_path_need` as the LAST step of
`optimize_indexed` (after pushdown and orientation, since the answer depends on what reads the
path in the final tree). `CountOnly` records each row's `(node count, edge count)` in a new
`Lineage::elem_counts` and skips the chain walk entirely.

Clean A/B against HEAD, three runs each side, same fixture (50,000 nodes, degree 3), min-of-3:

| row                             | baseline | count-only |                 speedup |
| ------------------------------- | -------: | ---------: | ----------------------: |
| anchored + `path_length(p)`     |   21,905 |  **6,999** |               **3.13x** |
| both ends anchored (early stop) |   17,237 |  **5,422** |               **3.18x** |
| `y.name` (lineage-free control) |    6,744 |      6,655 |               unchanged |
| anchored + `nodes(p)`           | ~281,000 |   ~281,000 | unchanged, as predicted |

`path_length(p)` now costs within 4% of projecting an ordinary property over the same 47,007
rows. Cumulative over items 41 and 43: **27,687us -> 6,999us, 4.0x.** `nodes(p)` is untouched
because its cost is `path_node_values` rendering element maps, which suppression cannot reach —
item 41 predicted exactly that, and the number confirms it.

### Three representations, one accessor

`elem_counts` empty means the elements are materialized and the sizes are the `offsets` /
`edge_offsets` spans. Non-empty means the elements were never built and the counts are the
truth. `Lineage::node_count_at` / `edge_count_at` are the ONLY readers that know which, so
`PathPart::Length` and `Cardinality` (exec/evaluator.rs) now go through them instead of
`edges.len()` — correct in both representations, and unconditional.

`offsets` stays an honest prefix-sum over the empty `values`, all zeros. That is the whole
difference from item 41's sketch, which would have carried the lengths IN the offsets: `path_at`
slices `values[offsets[i]..offsets[i + 1]]`, so non-zero offsets over an empty `values` is an
out-of-range slice. `try_shortest_early_stop` gathers directly, so an ordinary
`WHERE y.name = …` after a shortest path would have panicked.

Derivers: `gather` reorders the counts, `extend` adds (1 node, 1 edge), `extend_nodes` adds
(1 node, 0 edges), `push_step` carries them, `concat` normalizes MIXED arms to suppressed by
taking the materialized arms' sizes through the accessors, and the four seeds materialize so
they carry none.

### What the marking may and may not descend through

`scan_path` in exec/render.rs is now shared by `needs_lineage` and a new
`needs_path_elements`, parameterized by a leaf predicate. Sharing it is the safety property:
that walk enumerates every `Plan` and every `Expr` variant with no wildcard, so a variant added
later fails to compile until classified — a second hand-written walk would instead keep
answering "no element read" for the new shape, and suppressing a path somebody reads is a wrong
answer.

`CountOnly` is set only when `needs_lineage && !needs_path_elements`, so a size read ALONGSIDE
an element read keeps everything materialized (one sidecar serves both).

The marking walk descends only through operators that leave the path alone or merely GATHER it
(Project, Filter, Aggregate, Distinct, OrderPage, Tail, Enumerate, Sample, DistinctBy) and
stops at anything else. A whitelist, not a blacklist, because the directions are asymmetric:
not marking costs performance, marking under an operator that REBUILDS the path is a wrong
answer.

### Two bugs the new oracle caught, on its first run

Both were found by `rewrite_fuzz` within seconds of the mode compiling, and neither by any
unit test at that point.

1. **`elem_counts` ran short of the row count** — `index out of bounds: the len is 14 but the
index is 14` inside `Lineage::gather`. `shortest_path` emits from FIVE places (the Any and
   All arms plus three in the cycle-closing block) and only Any had been taught the mode. Fixed
   by threading the mode into `push_path` itself, so every call site is handled by construction
   and the compiler enumerates them — a mode branched per site is a mode one site forgets.
2. **Seed 632: a `VarLength` above the `ShortestPath`.** It rebuilds the path through
   `path_at`, which on a suppressed lineage reads an EMPTY prefix, so everything the shortest
   path contributed vanished: `cardinality(p)` came back 3/5/7 raw and 0/2 optimized. This is
   what produced the whitelist above.

### Tests, and one the unit tests could not catch

Six new tests in `exec/tests.rs`; the four ceiling tests from item 40 now use `nodes(p)`
(`ALL_PAIRS_NODES`) since `path_length` no longer materializes and so no longer tests element

| ------------------------------------------------------- | ----------------------------- |

## 42. The optimizer fuzzer had never once compared a path (2026-09-30)

Item 41 recorded that putting the count-only decision on `Plan::ShortestPath` "buys a free
oracle", since `rewrite_fuzz` compares raw against optimized as multisets. **That oracle did
not exist.** `grep -n 'PathAccess\|path_length\|PathPart' opt/rewrite_fuzz.rs` matched nothing:
the generator emitted `ShortestPath` (346/2000 plans), `VarLength` (429/2000) and
`RepeatGroup` (315/2000), and then projected only slots, `count(*)` and numeric aggregates. So
every lineage-producing operator was generated and its lineage was never read. A count-only
mode built behind that oracle would have been built behind nothing.

This is the same wall as items 38 and 39, in a new place: the operator was reachable, the
PROPERTY was not.

FIXED: `Gen` gains `tracks_path`, set wherever `VarLength` / `ShortestPath` / `RepeatGroup` is
generated, and the canary arm of the terminal projection now also projects
`Expr::PathAccess { part }` one time in three when the plan produces a path. It rides the
canary rather than taking an arm of its own, so the slot-permutation sensitivity that arm
exists for stays in the same rows, and the seed-to-plan mapping shifts as little as possible.

`Length` and `Cardinality` only, deliberately: both are plain numbers, so comparing them as a
multiset cannot report a false difference the way comparing rendered element maps might.

> **The worry was UNFOUNDED — item 58 (2026-09-30).** An element map is byte-deterministic
> (labels sorted, properties in already-sorted `prop_keys()` order), so the element accessors are
> generated now too. Checking it also found that NO oracle read a rendered path element.
> `nodes(p)` / `edges(p)` / `Elements` return lists of maps and are left for a widening that
> means to take on map-ordering as a question. `tracks_path` is also deliberately FALSE across a

Measured density: **path-proj 80/2000 plans**, 0 faulted. Floor asserted at half the measured

the mid-pattern-split coverage nearly drifted away (see the note on that floor).

Deep sweep clean: `LENKE_OPT_FUZZ_SEEDS=200000` green in 42s. No existing lineage bug — the
coverage is new, the engine was already right.

### Teeth, proved in both directions

The usual mutation check is not enough here, because the thing to establish is that the NEW
coverage is what catches the bug. A lineage bug in shared code (say `PathPart::Length` reading
`edges.len() - 1`) is invisible to this oracle by construction — it corrupts raw and optimized
identically, and the two sides are all it compares. So the mutant has to be one OPTIMIZING
introduces. Injected in `optimize_indexed`: after the rewrites, rewrite any projected
`PathPart::Length` to `PathPart::Cardinality`. Row count untouched; only the projected path
VALUE differs between the two sides.

- Mutant **with** the path projection: `optimizing_preserves_rows_{with,without}_indexes`,
  `_across_shapes` and `_across_sizes` all FAIL.
- Same mutant with the path projection disabled (`if false && …`): all four PASS. The only
  failure is `the_generator_actually_reaches_the_rewrites`, and that is the new floor
  reporting the coverage loss — the floor doing precisely its job.

That second run is the evidence that matters: it is the old generator, and it is blind.

### Why the count-only optimization is still not built

Item 41's plan was to suppress the lineage value vectors and carry `offsets` as a length
prefix-sum. **That design is unsafe and would have panicked in production.** `Lineage::gather`
(lenke-engine-core/src/batch.rs:235) rebuilds values with
`values.extend_from_slice(self.path_at(i))`, and `path_at` slices
`values[offsets[i]..offsets[i+1]]` — so empty values with non-zero offsets is an out-of-range
slice, not a clever encoding. `try_shortest_early_stop` calls `sp_batch.gather(&keep)` directly
(exec/reverse.rs), so an ordinary `WHERE y.name = …` after a shortest path would have hit it.
The invariant "nothing calls `path_at` in this mode" cannot be held by a plan predicate, because
the derivers call it regardless of what the plan reads.

So the mode needs the hop counts carried EXPLICITLY (a parallel `Vec<u32>` on `Lineage`, with
`offsets` kept as honest indices into an empty `values`), and then the failure mode of a deriver
that forgets to propagate it is a WRONG ANSWER rather than a panic. That is the failure mode this
audit's own equivalent-spellings section calls the worst kind, and it is why the oracle had to
come first. It now exists, with verified teeth, so the mode can be built behind it.

### Why the count-only mode was not built yet

It needs the plan-global fact "the path is read, but only as a count" to reach
`varlen::shortest_path`. Three routes were considered and the cheap one was taken first:

- Widen `track: bool` to a mode enum — 133 sites take `track`, 36 use it as a bool. Mechanical
  but wide, and a wrong edit silently changes lineage behavior.
- A field on `Lineage` — only 4 struct literals, but 9 derivers (`seed`, `seed_edges`,
  `seed_steps`, `empty`, `push_step`, `gather`, `extend`, `extend_nodes`, `concat`) would each
  have to propagate it, and one that drops it suppresses values that a reader still wants.
- **A field on `Plan::ShortestPath`, set by the optimizer.** The decision is plan-global
  analysis, which is where that belongs, and it buys an oracle: `rewrite_fuzz` compares raw
  against optimized as multisets, so the raw plan (full lineage) and the optimized plan
  (count-only) must return identical rows.

  > **CORRECTION (item 42).** That oracle did NOT exist — the generator projected no path of
  > any kind, so it had never compared lineage at all. It has since been built and its teeth
  > proved in both directions. Also corrected there: the offsets-as-length-prefix-sum design
  > sketched below is UNSAFE and would have panicked, because `Lineage::gather` rebuilds values
  > through `path_at` regardless of what the plan reads.

The third is the intended route. Whichever is used, suppressing the value vectors makes
`offsets` stop being an index into `values` and become a length prefix-sum, so `path_at` /
`edges_at` must never be called in that mode — an invariant held only by the plan predicate.
`PathPart::Length` and `PathPart::Cardinality` should therefore read the offset DIFFS rather
than `edges.len()`, which is equivalent in both modes and makes the evaluator change

## 40. `ANY SHORTEST` with a path projection OOM-killed the process at 6,000 nodes (2026-09-30)

An unbounded `MATCH p = ANY SHORTEST (x)-[:R]->*(y) RETURN path_length(p)` emits one row per
(source, reachable target) — quadratic in node count — and nothing bounded it. Measured on a
degree-3 fixture, peak RSS read from the cgroup's `memory.peak` per run:

| nodes |       rows | path elements | post-run RSS |           **true peak** |
| ----: | ---------: | ------------: | -----------: | ----------------------: |
| 1,000 |    945,058 |     5,706,847 |      44.7 MB |                  560 MB |
| 2,000 |  3,748,158 |    25,095,526 |     157.6 MB |                 2.41 GB |
| 4,000 | 15,072,270 |   110,513,050 |     611.5 MB |            **10.43 GB** |
| 6,000 |          — |             — |            — | **OOM-killed at 16 GB** |

Three things this measurement settled, each of which had been guessed wrong first:

- **Streaming was never the protection.** The intuition was that shortest path is intensive
  so it must be streamed. It is not: `streaming_chain` (exec.rs:2270-2385) accepts exactly
  eight plan nodes — `Scan`, `IndexSeek`, `RangeSeek`, `Filter`, `Expand`, `VarLength`,
  `Project`, `EdgeVertex` — and `ShortestPath`, `RepeatGroup` and `OptionalExpand` fall to
  `_ => None`. Shortest-path plans are MATERIALIZED. Nor would streaming have helped: the
  block loop accumulates with `acc.push` and concatenates, so peak includes the full result
  either way; it shrinks per-hop intermediates, and shortest path has none to shrink (its BFS
  state is per-input-row and dropped each iteration).
- **A post-hoc guard could not have worked.** `guard_intermediate` (exec.rs:2154) reads
  `batch.rows()` once the batch already EXISTS, which is fine where the batch is cheap and the
  risk is a later `read_property` — but here the batch IS the allocation that fails. The check
  has to be incremental.
- **Rows are the wrong unit, by 20:1.** At 4,000 nodes the query was 15.1M rows but 110.5M
  path elements, and peak tracked the elements (~94 bytes each), not the rows. Rows at the
  6,000-node kill were ~34M — BELOW the 50,000,000 default — so a row-counting guard would
  not have fired before the OOM at all. The guard's own message shows the split on the bench
  fixture: `2,397,360 rows plus 48,562,936 path elements`.

FIXED: `varlen::guard_path_growth`, checked once per input row at the top of the loop in BOTH
`shortest_path` and `shortest_k_path` (the `SHORTEST k` trail enumerator is a separate
function and needed its own call). Unit is rows + materialized path elements, charged against
the existing `intermediate` ceiling — one knob, already plumbed through
`ConfigId::LimitsIntermediate`, and counting values is as portable as counting rows (exact
integers, identical on 32- and 64-bit). `shortest_path`/`shortest_k_path` now return
`Result<Batch, String>`; `try_shortest_early_stop` returns `Option<Result<Batch, String>>`.

After: peak is bounded FLAT at ~1.98 GB at 2,000 / 4,000 / 6,000 nodes (vs 2.41 GB / 10.43 GB
/ OOM), and the 6,000-node case reports `E_RESOURCE_EXHAUSTED` instead of killing the process.

**Behavior change, deliberate:** 2,000 nodes now fails where it previously completed using
2.41 GB. Accepted — an unbounded all-pairs shortest path is quadratic and must fail at SOME
size; the only question is whether it fails cleanly, and 2.4 GB already aborts the wasm module
(32-bit) rather than erroring. The realistic shape is untouched: an anchored source over
**200,000 nodes** is 188,191 rows, 164 ms, 321 MB peak — 4.3M charged against a 50M ceiling.

**Native-only, consistent with precedent.** The pure-TS engine enforces no `intermediate`
ceiling anywhere, so a query that now throws on native still succeeds in pure-TS. That is the
pre-existing and settled shape of `guard_intermediate` (native/wasm anti-runaway, not
semantics) rather than a new divergence class — see [[wasm-oom-intermediate-guard]]. On the
CLI, which sets `intermediate` to 10,000,000 for wasm, this is strictly an improvement: a
catchable error instead of an `unreachable` that kills the REPL.

| shape                                          |                best_us |   rows | vs control |
| ---------------------------------------------- | ---------------------: | -----: | ---------: |

### A mutant took the machine down, and the lesson is about mutant DESIGN (2026-09-28)

The first attempt at the block-boundary mutant was `min(ids.len())` → `min(ids.len() - 1)`.
That does not produce a wrong answer — it stops the loop ADVANCING. `start = end` where `end`
is capped at `len - 1` means once `start` reaches `len - 1`, `end == start` forever, and the
loop pushed a `Batch` per iteration until RAM was gone, then spent hours filling a 192 GB
swapfile with nothing killing it. The machine needed a hard reboot, and the reboot wiped the
`/tmp` backup, so the mutated line had to be reconstructed from `git diff`.

Two things came out of it, both now in `CLAUDE.md` under "Changing a planner rewrite":

1. **A loop bound, a `while` condition and an index cap are where an off-by-one stops being a
   wrong answer and becomes non-termination.** Check the advancement expression before
   running. For this loop the property is `end > start` strictly; the replacement mutant
   `start = end + 1` probes the same boundary and advances by 8,193.
2. **Every mutant runs under a timeout AND a memory cap**, because the two catch different
   failures — a non-allocating infinite loop never trips `MemoryMax`. Both were verified
   empirically on this box before being relied on: an allocator bomb dies in under a second
   with exit 137 and swap stays at 0 MB, a bare `while true` is killed with exit 124. The cap
   is 16G, sized from measurement rather than a round number — peak RSS is 1.86 GB for the
   whole suite and 1.53 GB for a 200k-seed sweep, so 16G is ~8x the real ceiling while
   leaving ~45 of this box's 61 GB free, which is what keeps the machine usable.

A THIRD SURVIVOR EXPLAINED, since two of the three original mutants did not change anything.
`end = start + BLOCK - 1` survived and SHOULD have: it makes blocks 8,191 wide instead of
8,192, and they still tile `[0, len)` exactly with no id skipped or repeated. Block size is
arbitrary. (The other non-result was a mis-applied mutation — an anchor that matched three
sites, and a shell that split the replacement on the `::` in `Batch::single`. A mutation that
did not apply reports as "survived" and means nothing; assert the anchor is unique and check
that the edit landed.)

## 32. Fuzzer: a second oracle that can judge a PERFORMANCE decision (2026-09-27)

Item 29 established that `optimizing_preserves_rows_*` is blind to any choice where both
branches are correct — and the seek-vs-scan gate is exactly that. Seeding an index and
leaving a `Filter(Scan)` return the same rows, so the gate from item 18 shipped with no
generative coverage: making `seek_beats_scan` return `true` unconditionally passes every
seed. This is the oracle that closes it.

- [x] **[med]** engine `opt/rewrite_fuzz.rs` —
      `a_seek_is_chosen_exactly_when_the_predicate_is_selective`, added 2026-09-27. It
      asserts the DECISION rather than the rows: across ~30 `(key, op, literal)` triples on
      the indexed keys, spanning one row in 9,000 up to nearly everything, a selective
      predicate must reach the index and an unselective one must not.

  WHY IT IS NOT A TAUTOLOGY, which was the whole risk. The obvious expectation is to ask
  `seed_fraction` what the selectivity is — the planner's own estimator — so the test would
  assert only that the planner agrees with itself, and a miscounting `range_count_capped`
  would satisfy both sides. Instead the true selectivity is MEASURED BY EXECUTION: run the
  UNOPTIMIZED `Filter(Scan)` and count its rows. That is ground truth by definition, touches
  none of `seed_fraction` / `range_count_capped` / `index_bucket_len`, and avoids
  reimplementing three-valued comparison in the test, where a mistake would look like an
  engine bug. The threshold constant is shared on purpose: `SEEK_MAX_FRACTION` is a policy
  number, not a computation, and it is the MEASUREMENT that has to be independent.

  It finally gives the 9,000-node fixture from item 29 a specific job: below
  `SEEK_FLOOR_NODES` the gate returns `true` unconditionally and there is no decision to
  check, so this test asserts the fixture clears the floor.

  FOUR POISONS, and the fourth is the one that justifies it:

  ```text
  seek_beats_scan -> always true      caught (also by 3 unit tests)
  seek_beats_scan -> always false     caught (also by 3 unit tests)
  the equality half of the gate gone  caught (also by 2 unit tests)
  seed_fraction wrong ONLY for 5-12%  caught by THIS TEST ALONE — 747 others pass
  ```

  The last one is the reach a sweep has and hand-picked cases do not: the unit tests use ~1%
  and ~20-49% selectivities, which straddle a mispriced middle band without entering it. A
  cap off by one, or an estimator wrong in a narrow range, lands there.

  A band of ±0.02 around the threshold is SKIPPED rather than asserted, because the cap is a
  `ceil` and a fraction sitting on the line can round either way; encoding that as an
  expectation would be encoding an off-by-one. The test asserts at most 4 cases land in the
  band, so the skip cannot quietly swallow everything.

## 29. Fuzzer: the oracle's reach is "things the optimizer rewrites" (2026-09-27)

Chasing the sub-`SEEK_FLOOR_NODES` gap turned into a finding about what
`optimizing_preserves_rows_*` can and cannot judge. That reframes the remaining fuzzer
work, so it is written down before any more of it.

THE STRUCTURAL LIMIT. The oracle compares a plan against its optimized self. It can
therefore see a bug ONLY where the two sides differ — where the optimizer changed
something, or where a fast path it routed to disagrees with the enumeration the other
side does. It is blind to:

- a bug in a primitive BOTH plans share (item 28's multi-label probe);
- a bug in a node the optimizer does not rewrite, which appears identically on both
  sides (`DistinctBy`, below);
- any PERF-only decision, since both branches are correct by construction.

Three separate attempts this session ran into that wall, which is why it is now stated
here rather than rediscovered a fourth time.

- [x] **[low]** engine `opt/rewrite_fuzz.rs` — a 9,000-node fixture added
      (`optimizing_preserves_rows_across_block_boundaries`, `fixture_sized`), kept as
      DIVERSITY coverage and labelled as such. Above the floor the gate changes which plans
      seed — 318 plans per 2,000 contain a seek at 24 nodes against 158 at 5,000 — so the
      plan pairs differ from the small fixtures', and a rewrite wrong only when a seed is
      DECLINED can only be caught here. Same justification `across_fixtures` already runs
      on. 2.09s at the default budget.

  WHAT IT DOES NOT COVER, each established by injecting a panic rather than assumed, and
  each recorded at the test:

  - the gate itself — perf-only, so oracle-blind;
  - the selectivity probe — `seed_fraction` is already reached by every other test, because
    `orient_is_worth_it` consults it with NO floor;
  - `exec/order.rs`'s 2,048-row block-streamed dedup and `exec.rs`'s 8,192-row streamed
    projection. Neither is reachable from generated plans at ANY fixture size. The first
    needs `streaming_chain` to accept the chain and it has no arms for the `ShortestPath` /
    `RepeatGroup` / `OptionalExpand` hops the generator mixes in; the second is cost-gated
    and never entered. These are named holes with a reason, not something size fixes.

- [~] **[low]** generating `Plan::DistinctBy` — TRIED AND REVERTED, for two measured
  reasons. It is the one IR node the generator has never emitted, so it looked like an
  obvious gap.

  1. With a PARTIAL key it is ORDER-SENSITIVE: it keeps the first row per key, and the
     optimizer may legitimately change arrival order, so the result is genuinely
     unspecified. The fuzzer reported a false failure within seconds (seed 7220: group `n4`
     raw against `n3` optimized). Confirmed as order-sensitivity and NOT a pushdown bug by
     the discriminating test — with the key covering every slot, which makes it
     content-stable, all seeds pass. This is consistent with the repo's order-is-unspecified
     policy; `dedup('a')` over an unordered stream is `SELECT DISTINCT ON (a)` with no
     ORDER BY.
  2. With a FULL key it is oracle-invisible, per the limit above: poisoning
     `distinct_by_keep` to dedup nothing leaves every seed passing.

  So the shape needs a differential (TS-vs-native) oracle. Recorded at the site so the next
  reader does not repeat the attempt.

## 27. Filter(Scan) materialization: scoped, one part taken, the rest declined (2026-09-27)

Item 18's last open note, and the last lead of this sweep. Scoped rather than started, which
is the result.

- [x] **[low]** engine `exec.rs` — TAKEN. Every seed site (`Scan`, `NodeSeed`, both seeks, and
      their capped twins — eight in all) built its `Col` from a CLONE of the id vector and
      then read the original to fill lineage. On an untracked query, which is nearly all of
      them, that was a whole extra id vector copied for nothing — 800KB on a 200k scan. The
      lineage is now taken off the slice first and the ids are MOVED in.

  Worth **1-5% and no more**: `Filter(Scan)` on a 20% predicate 289.0us -> 275.4us, a bare
  scan projection 1044.8us -> 1029.6us, a hop off a scan flat. That is AT this repo's noise
  floor, so it is kept for being strictly less allocation and copying for identical output,
  NOT on the strength of those numbers. The comment at the site says so.

- [~] **[med]** the actual materialization gap — DECLINED, with the scope written down.

  `Filter(Scan)` is 275.4us where the scan-fallback `IndexSeek` doing the same work is
  194.6us, because the filter builds the whole 200k-row batch and then compacts a keep list
  to 40k, while the seek's fallback emits only survivors as it walks.

  GOOD NEWS FIRST: this needs NO IR change. The framing that it wants a new physical operator
  is wrong — the engine already has the operator, it IS the scan-fallback `IndexSeek`, and a
  fused scan+filter would live entirely inside `exec`'s `Filter` arm as a special case for
  `Filter { input: Scan, .. }`. No new `Plan` variant, so no codec, wasm or TS-parity
  surface.

  WHY IT IS STILL NOT SMALL: `try_filter_keep` operates on a `Batch` — it takes the batch's
  id column and indexes the storage columns by row. A fused version needs those same typed
  fast paths driven by an ID ITERATOR instead, across roughly eight arms (Str, Dict, Num,
  Bool, the edge-property path, the `Not` De Morgan path, and the two disjunction paths).
  Either they are re-expressed generically over an id source, or they are duplicated — and
  duplicated slot/predicate logic is what produced the two crossed-slot bugs and the
  `for_each_nbr`/`slice_degree` mirroring hazard already recorded here. Lineage is a second
  consumer: a tracked `Filter(Scan)` must still produce per-survivor lineage, which the
  gather currently gets for free.

  So: a ~1.4x on one shape (an unselective equality where an index exists but is declined),
  against a refactor of the vectorized filter's whole dispatch. That is the right trade to
  make deliberately at the start of a piece of work, not at the end of a sweep. Recorded here
  so the next person starts from the scope rather than from the measurement.

  So declaring the index cost **2.03x** on a count and 1.79x on a projection; both are now at
  parity with not declaring it. `slice_degree` had inherited the same precedence and is fixed
  in lockstep — it must mirror `for_each_nbr` or it reports a degree for a different edge set.

  The index remains the FALLBACK, and not vestigially: the CSR overlay is dropped by any
  adjacency write and rebuilt in bulk, while the index is maintained incrementally, so on a
  write-heavy store the CSR returns `None` and the index is what keeps a typed hop off the
  flat scan.

  WHY THE SWAP IS SOUND: both are built by walking `out_adj` in order, so they yield the same
  edges in the same order and the precedence is a pure cost choice. Pinned by
  `the_type_csr_and_the_edge_type_index_agree_edge_for_edge`, which records every
  (neighbour, edge) pair for every node, direction and type with the overlay fresh, then
  invalidates it with a write and demands the index produce the identical sequence. Reversing
  the index bucket's iteration turns it red.

  TWO SURVIVING MUTANTS, and they are the point rather than a gap: removing the index
  fallback, or removing the CSR path, changes no answer — each falls through to another
  structure that yields the same edges in the same order. That all three agree is exactly
  what makes this a cost decision, so the benchmark covers it and no unit test claims to.

### The two declines, measured and LEFT ALONE (2026-09-27)

Both were deliberate and documented; neither had a number attached. Now they do.

- [~] A type DISJUNCTION (`-[:RARE|T0]->`) must not union buckets — that reorders against the
  flat stored-order scan and would break byte-identity. It costs NOTHING: 1072.3us
  unindexed against 1013.2us indexed, because both walk the adjacency anyway. No reason
  to revisit it.

- [~] A graph with ANY multi-label edge skips BOTH structures, since each keys on an edge's
  primary label and would miss a `:Y` match on an `[X, Y]` edge. This one is expensive —
  2290.7us against 151.0us, **15x** — and one secondary label anywhere disables it for the
  whole graph. NOT attempted: serving the primary matches from the CSR and then sweeping
  for secondary ones would emit them in two groups rather than in stored order, which is
  the same byte-identity objection that rules out unioning disjunction buckets. Closing it
  properly needs a per-type structure that carries secondary labels, which is a storage
  change, not a dispatch change. The index state is irrelevant here (2290.7us against
  2245.0us with it), so this is the cost of the decline itself.

## 16. GQL: `OPTIONAL` over a match BLOCK is unimplemented (2026-09-21)

- [~] **[med]** engine `gql.rs:1062` — `OPTIONAL MATCH …` parses, but the ISO
  grammar allows `OPTIONAL` over a braced or parenthesized BLOCK of match
  statements, and both are rejected with "expected MATCH after OPTIONAL". Verified
  against the ISO/IEC 39075 BNF digital artifact:

  ```text
  <optional match statement> ::= OPTIONAL <optional operand>
  <optional operand> ::=
      <simple match statement>
    | <left brace> <match statement block> <right brace>
    | <left paren> <match statement block> <right paren>
  <match statement block> ::= <match statement>...
  ```

  So the implemented form is the degenerate single-statement case. The block forms
  matter beyond syntax: `OPTIONAL { MATCH a MATCH b }` is one left-outer over the
  JOINT pattern, which is not expressible as two consecutive `OPTIONAL MATCH`es (that
  is two independent left-outers). A user wanting "either both hops or neither" has
  no spelling today.

  Not a Cypherism — `OPTIONAL MATCH` is genuinely ISO; it shares the spelling with
  Cypher by convergence. Worth confirming because the reverse mistake (assuming a
  Cypher-looking keyword is a Cypherism and removing it) would be worse.

  DIAGNOSED, NOT BUILT (2026-09-21): the block forms now fail with
  `E_NOT_IMPLEMENTED` and a message saying the query is valid ISO, instead of
  `E_SYNTAX` "expected MATCH after OPTIONAL" — which was wrong twice over, since
  `{` IS what the grammar expects there and the user had made no mistake.

  `E_NOT_IMPLEMENTED` rather than `E_UNSUPPORTED` deliberately. The vocabulary
  distinguishes them — "recognized but not yet implemented" vs "a feature that
  isn't supported" — and the difference tells a reader whether to work around it
  forever or wait for it. This engine intends to accept ISO, so it is the former.
  SWEPT 2026-09-21. The engine had no uses of `E_NOT_IMPLEMENTED` at all; it now
  has 15, and the split is:

  - **Reclassified to `E_NOT_IMPLEMENTED`** — Gremlin query parameters (`ffi.rs`,
    whose own comment said "not… yet"), the unbuilt command tiers (whose message
    already read "is not yet implemented"), and 13 parse-time messages in
    `gql.rs`/`gremlin.rs` that literally said "not supported yet" while surfacing
    as **E_SYNTAX** — telling a user they had made a typo when the message itself
    said otherwise.
  - **Left as `E_UNSUPPORTED`** — a branching step inside a filter body
    (`exec.rs`), which tells the caller to RESTRUCTURE, and a map/record property
    in flat PG-text (`codec.rs`), which is a format limitation. Neither is coming.

  (My earlier "12 uses" was a raw grep count including comments and doc lines;
  there were four error-raising sites, two of which moved.)

  `set_exec_error` and both parse-error ladders learned the code, so it survives
  the FFI boundary; verified end-to-end that the prefix is stripped and the
  user-visible message is unchanged. A test pins the distinction in BOTH
  directions — an unbuilt construct must not read as a syntax error, and a real
  syntax error must not claim to be unimplemented.

## 14. Exec: UNION with a narrower right arm panicked (2026-09-19)

- [x] **[high]** engine `exec.rs` — FIXED 2026-09-19, found while teaching
      `opt/rewrite_fuzz` to generate set operations. Reachable from ordinary GQL and a

## 13. Exec: an interval-index seek ignored the hop's edge type (2026-09-19)

- [x] **[high]** engine `exec.rs` `interval_expand` — FIXED 2026-09-19, found by
      `opt/rewrite_fuzz` on its first run after learning to generate bound edge
      variables. The RI-tree is keyed on the interval alone and knows nothing about
      edge types; the SEEK path pushed every overlapping edge without consulting
      `want`, while the SCAN path had always filtered correctly via `for_each_nbr`.

  So `MATCH ()-[r:T]->() WHERE r.lo <= $x AND r.hi >= $y` returned edges of EVERY
  type as soon as an interval index existed. **Creating an index changed the
  answer**, silently, on exactly the bitemporal "as of" query the index exists to
  serve ([[bitemporal-interval-index]]).

  Nothing caught it because the bug needs an index AND a type filter together, and
  every hand-written test covering interval overlap had one edge type or no index.
  Fixed with `eid_carries_wanted` (the eid-based twin of `edge_carries_wanted`,
  consulting the whole label set so multi-label edges match identically either
  way), plus a regression test whose fixture puts an A-edge and a B-edge over the
  same interval, so ignoring the type returns exactly twice the rows.

## 12. Planner: Expand pushdown was all-or-nothing, so a label froze a seek (2026-09-17)

- [x] **[high]** engine `opt.rs` — FIXED 2026-09-17, found while checking item 11's
      premise. The predicate-pushdown arm for `Expand` guarded on `refs_below` over the
      WHOLE predicate, so a MIXED conjunction refused to push at all. That is not an
      exotic shape: `(a:Person)-[:KNOWS]->(b:Person) WHERE b.age > 98` lowers to two
      stacked filters, the merge rule fuses them into one `And`, and from then on the
      slot-1 label check pinned the slot-0 range predicate above the hop. The seek never
      happened and the walk ran from every Person.

  **Writing a label made the query 300x slower** — 9382us against 31.6us for the
  same query with the far node left unlabelled. Worst kind of cliff: more
  information given to the planner, worse plan out.

  The fix is the split the VarLength and ShortestPath arms had already been given
  for exactly this reason (opt.rs's own comment: "otherwise a mixed `a.age = 1 AND
b.age = 2` refuses to push at all and the walk runs from every node"). Now 9382us
  -> 446us, and the forwards/backwards spellings optimize to the SAME plan, so the
  probe reports "identical optimized plan" rather than a time that happens to match.

  One trap worth keeping: the arm needs an `any_pushable` match guard. Without it
  it matches EVERY `Expand` and starves the interval-overlap fusion arm below,
  whose predicate reads the bound edge slot and is pushable by nothing — silently
  disabling interval seeks for every bitemporal query. Two tests pin both halves.

  Also fixed here: `spelling_probe`'s fixture had NO index, so every group about
  whether a predicate reaches an index was measuring something else.

### Remaining: `_MERGE` write-clause composition (deprioritized)

TS parses the clause pipeline uniformly, so ANY clause composes after `_MERGE` (`_MERGE … SET …`,
`_MERGE … MATCH … RETURN`, `MATCH … _MERGE …`). Native treats `_MERGE` (like `INSERT`) as a
statement-leading write command with only a read tail (now incl. RETURN). So `_MERGE … SET …`
is accepted in TS (`SET` yields no rows) and `E_SYNTAX` in native. Per the user, a bare `SET`
after `_MERGE` is the redundant/verbose spelling (put the value in the pattern — `_MERGE` already
sets it), so this is deprioritized. A full fix means making native `_MERGE`/`INSERT` first-class
composable pipeline clauses — a larger structural change, separate from the RETURN work. Not
fuzzer-covered (the differential fuzzer does not generate `_MERGE`).

### Container-body mutations — DONE (2026-09-07); write-aware execution model shipped

Delivered the write-aware container model (`d8625e13` map/repeat, `a1a8aefb` union/choose),
byte-identical to TS on the tested shapes:

- **`write_frontier(plan, &mut store)`** — the write-side counterpart of `pull`: runs a write
  step (or nested write chain) and returns the CREATED elements as a frontier batch. Handles
  `AddVertexStep`, `AddEdgeStep` (EdgeEnd Slot/ExtId, `E_MISSING_VERTEX` on unresolved), and

- **`map(<write>)`** — lowered to the per-traverser write step. DONE.
- **`repeat(addV('L')).times(N)`** — a dedicated parse branch building N chained AddVertexSteps

- **`union(addV('A'), addV('B'))`** — a `Plan::Union` of AddVertexSteps sharing the input; each

- **`choose(cond, addV('X'))`** (no else) — lowered to `Union { write over filter(guard),
passthrough over filter(not guard) }`; matching rows get a created vertex, the rest pass through.

### Still open — GQL, low-priority polish (deferred, 2026-09-08)

- **Mid-query `<named procedure call>` in the linear pipeline** — `call_named_form_is_deferred`.
  Top-level `CALL name(args) YIELD` already works (the algorithms catalog) and correlated
  inline `CALL (scope) { … }` subqueries already work; the only gap is a NAMED procedure call
  appearing as a `<call query statement>` MID-pipeline (after a `MATCH`, args referencing outer
  bindings). Deferred, well-justified: mid-query named-`CALL` is not table-stakes for ISO-GQL —
  Microsoft Fabric Graph (a GA'd ISO-GQL implementation) ships with NO `CALL` at all (its whole
  statement set is MATCH/LET/FILTER/ORDER BY/OFFSET/LIMIT/RETURN), so lenke already EXCEEDS the
  reference implementations on procedure support. Revisit only on a concrete use case
  (source-parameterized procedures — rooted pagerank, single-source shortest path — are the real
  per-row case).

  GRAMMAR NOTE (verified against the ISO BNF + TuGraph ANTLR grammar): the ISO
  `<named procedure call>` is `name(args) [YIELD …]` with **NO** `<variable scope clause>` — the
  `(scope)` clause attaches ONLY to the inline `{ }` form. A named call correlates via its
  ARGUMENT expressions referencing in-scope binding variables + linear composition, not via a
  scope clause (and not via Cypher's positional per-row rule — this engine targets ISO-GQL). See
  [[iso-gql-reference]].
